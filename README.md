# 오락실 파인더 + 리듬게임 커뮤니티 — 프로토타입

리듬게임 유저를 위한 두 서비스의 프로토타입입니다. 게임/기종 마스터(`machines`)와
플레이어(`players`)를 공유하므로 하나의 앱 안에 여러 라우트로 들어가 있습니다.

**1. 오락실 파인더** — 내 주변 오락실 지도

| 경로 | 기능 |
|---|---|
| `/` | 오락실 CRUD(**수정은 관리자만**), 지도 표시, 보유 기종/반경 검색, **리뷰·평점**, **제보** (있어요 / 없어졌어요 / 지금 대기 N명 / 컨디션). 같은 게임이 2대 이상이면 **기체마다 카드가 갈리고 컨디션도 따로** |
| `/live` | **전국 실시간 제보 피드** — 방금 올라온 대기·컨디션·기종 변동을 한 화면에서 |

**2. 리듬게임 커뮤니티**

| 경로 | 기능 |
|---|---|
| `/tier` | **게임별 체감 난이도 서열표** — 같은 레벨 안에서의 체감 난이도를 클리어한 사람들의 투표로 배치 + **채보마다 평가(코멘트·성향 태그)** |
| `/community` | **리듬게임별 게시판** — 게임 탭(펌프 · 사볼 · IIDX · 태고 …) × 말머리(자유/질문/정보/공략/대회), 댓글·추천 |

두 서비스는 데이터로 이어집니다 — 오락실·기종·플레이어가 한 벌입니다:

```
오락실 제보 ─┐
서열표/평가 ─┼─ 같은 기종 마스터(machines) · 같은 플레이어(players)
게시판      ─┘

클리어 기록 → 그 채보의 체감 난이도 투표 자격 → 서열표에 반영
```

스택: **Next.js 16 (App Router) · TypeScript · PostgreSQL · 네이버 지도 API · zod**

## 빠른 실행

```bash
npm install
npm run dev
```

`http://localhost:3000` 으로 접속하면 시드 데이터가 바로 보입니다.
**DB 설치도, 지도 API 키도 없이 그대로 동작합니다** (아래 참고).

둘러보기·제보·글쓰기는 로그인 없이도 됩니다. 상단 네비의 **로그인** 에서 아이디/비밀번호,
**회원가입**(`/signup`), 소셜 로그인(Google·카카오·네이버) 중 하나를 고를 수 있습니다
([계정과 로그인](#계정과-로그인) 참고). 오락실 정보 수정과 삭제만 관리자 몫이고,
개발 환경의 관리자 기본값은 **`관리자` / `admin1234`** 입니다
([관리자 권한](#관리자-권한) — 운영에서는 반드시 바꾸세요).

소셜 로그인은 **키를 넣은 제공자만** 실제로 동작합니다. 키가 없는 버튼을 누르면 제공자로
보내지 않고 안내와 함께 로그인 화면으로 되돌아옵니다 (`.env.example` 참고).
소셜로 **처음** 들어오면 동의·인증이 끝난 자리에서 닉네임을 한 번 묻습니다 (`/welcome`).

## DB — 설치 없이 시작, 나중에 진짜 Postgres로

[`lib/db.ts`](lib/db.ts) 가 환경에 따라 두 드라이버 중 하나를 고릅니다.

| 조건 | 사용 엔진 | 저장 위치 |
|---|---|---|
| `DATABASE_URL` 없음 (기본) | **PGlite** — WASM으로 빌드된 내장 Postgres | `.pglite/` |
| `DATABASE_URL` 있음 | **PostgreSQL** (node-postgres) | 해당 서버 |
| `DATABASE_URL` 있는데 **연결 실패** | **PGlite** — 떠 둔 사본으로 내려갑니다 ([아래](#postgresql-이-안-뜰-때--로컬-사본으로-계속-돌기)) | `.pglite/` |

둘 다 진짜 Postgres 엔진이라 **SQL은 한 글자도 바뀌지 않습니다.** 프로토타입은 설치 없이
돌리고, 운영으로 넘어갈 때 `.env.local` 에 연결 문자열만 채우면 됩니다.

```bash
# .env.local
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/arcade_finder
```

```bash
npm run db:init    # 스키마 + 시드 적용 (기존 테이블 드롭 — 파괴적)
npm run db:reset   # .pglite 까지 통째로 지우고 새로 생성
```

### PostgreSQL 이 안 뜰 때 — 로컬 사본으로 계속 돌기

PostgreSQL 을 쓰기로 한 뒤에도 그 서비스가 멈춰 있으면(재시작 중, 노트북에서 꺼 둔 상태)
화면이 통째로 죽습니다. 그래서 **`.pglite/` 를 PostgreSQL 의 사본으로 떠 두고**, 못 붙을 때
그쪽으로 내려갑니다. 서열표·오락실 목록이 시드가 아니라 실제 데이터로 그대로 뜹니다.

```bash
npm run db:snapshot            # 무엇이 복사될지만 보여줍니다 (dry-run)
npm run db:snapshot -- --yes   # 실제로 뜹니다 — .pglite/ 를 새로 만듭니다
```

떠 둔 사본은 dry-run 이 보여준 행 수와 대조되고, 기존 `.pglite/` 는 `backups/` 로 옮겨집니다.
스키마는 `db/*.sql` 에서 새로 만들므로 오래된 사본에 컬럼이 빠져 있어도 상관없습니다
([`scripts/snapshot-pg-to-pglite.mjs`](scripts/snapshot-pg-to-pglite.mjs)).

내려가는 자리는 두 곳입니다 ([`lib/db.ts`](lib/db.ts) `createDbWithFallback`).

1. **서버가 뜰 때** — 연결 확인(`SELECT 1`)이 실패하면 처음부터 사본으로 시작
2. **돌던 중에** — 쿼리가 커넥션 오류로 실패하면 그 쿼리부터 사본으로 다시 실행

> [!WARNING]
> 사본으로 내려간 동안 **쓴 내용은 PostgreSQL 에 반영되지 않습니다.** 그래서 한 번 내려가면
> 프로세스가 사는 동안 돌아오지 않습니다 — 살아난 걸 감지해 왕복하면 그 사이에 쌓인 글·제보가
> 어느 쪽에도 온전히 없는 상태가 됩니다. PostgreSQL 을 살린 뒤 **서버를 재시작**하면 다시 붙습니다.
> 지금 어느 쪽으로 돌고 있는지는 `getDbStatus()` 가 알려주고, 내려갈 때 서버 로그에 이유가 찍힙니다.

폴백이 싫으면(운영에서 사본에 쓰는 것 자체가 사고라면) `.env.local` 에 `DB_FALLBACK=off` 를
넣으세요 — 연결이 안 되면 그냥 에러를 냅니다. 판정 기준은 "DB 에 못 닿았다" 뿐입니다.
제약 위반·문법 오류는 사본에서 다시 시도하지 않습니다
([`tests/db-fallback.test.ts`](tests/db-fallback.test.ts)).

PostgreSQL 서비스 자체를 다루는 명령은 (Windows · 관리자 PowerShell):

```powershell
Restart-Service postgresql-x64-18     # 재시작
Get-Service postgresql-x64-18         # 상태 확인
```


**밖에서 폴백을 알아채기 — `GET /api/health`.** 폴백 중에도 화면은 멀쩡해서 로그 말고는 알 길이 없었다.
이 엔드포인트가 `{status: 'degraded', checks: {db: 'ok', db_primary: 'fail'}, db: {driver: 'pglite', fallback: true}}` 를 돌려주므로
모니터링 도구가 `check.db_primary` 로 잡을 수 있다 (정상이면 `healthy`, DB 조회 자체가 실패하면 `503 unhealthy`).
[Pulse](https://github.com/mick243/pulse) 에 PROBE 대상으로 등록하면 응답시간·가동 여부와 함께 이 값이 차트와 알림 룰이 된다.

**실제 트래픽까지 보기 — 앱 계측 (`lib/telemetry.ts`).** `.env.local` 에 `PULSE_API_URL` 과 `PULSE_AGENT_KEY` 를 넣으면
(Pulse 대시보드에서 AGENT 대상을 추가하면 키를 한 번 보여준다) 두 가지가 켜진다:
- **라우트별 요청수·p95·5xx** — Next.js 가 내장으로 내보내는 OpenTelemetry 스팬을 `instrumentation.ts` 에서 받는다.
  라우트 파일은 하나도 고치지 않는다 (`lib/telemetry-node.ts`).
- **SQL 지문별 호출수·p95·에러·느린 쿼리(≥250ms)** — `lib/db.ts` 의 어댑터를 한 겹 감싸 PGlite·PostgreSQL 양쪽의 모든 쿼리를 잰다.
  SQL 은 `SELECT arcade_reviews` 처럼 동사+주 테이블 지문으로만 나가고 원문은 나가지 않는다.

30초마다 메모리 집계를 Pulse 로 보내며, 요청 경로에 얹히는 비용은 Map 갱신 하나다. 키가 없으면 계측 코드가 전혀 실행되지 않고,
Pulse 가 죽어 있어도 경고 한 줄만 남기고 앱은 영향받지 않는다. 대시보드에서는 `GET /api/arcades/[id]/reviews` 의 p95 와 그 뒤의
`SELECT arcade_reviews` p95 를 나란히 볼 수 있어 "느린 게 API 인가 쿼리인가"를 바로 가른다.
(서버리스에서는 인스턴스가 요청마다 사라져 이 방식이 맞지 않는다 — 상주 프로세스용이다.)

### 스키마

[`db/schema.sql`](db/schema.sql) — 오락실 파인더

- `arcades` — 오락실 (이름, 주소, 좌표, 영업시간, 24시간 여부, 메모)
- `machines` — 기종 마스터 (펌프, EZ2DJ, EZ2AC, 사볼, IIDX, 태고, DDR, maimai, 츄니즘, 유비트).
  목록 순서는 `sort_order` 로 정합니다 — `id` 는 보유 기종·제보·서열표가 참조하는 키라서
  순서를 바꾸려고 손댈 수 없습니다. 10 단위로 띄워 사이에 끼워 넣을 자리를 남겨 뒀습니다
  (EZ2DJ 는 나중에 갈라져 나와 `id` 는 10, 목록 자리는 15)
- `arcade_machines` — M:N. **크라우드소싱 대상**. "이 오락실에 이 게임이 있다"는 사실만
- `arcade_cabinets` — **기체 1대 = 1행** (`cabinet_no` 1호기·2호기, `condition` 1~5).
  대수는 이 테이블의 행 수입니다. 같은 게임이 2대여도 한쪽 발판만 죽어 있는 경우가
  흔한데, `cabinet_count` 숫자 + 컨디션 한 칸으로는 그 차이를 적을 자리가 없었습니다
- `arcade_favorites` — 즐겨찾기 `(player_id, arcade_id)`. 담을 값이 없어서 그 쌍
  자체가 PK 입니다 (`created_at` 은 "최근에 담은 순" 의 근거)
  ([`db/migrate-017-arcade-favorites.sql`](db/migrate-017-arcade-favorites.sql))

[`db/schema-tier.sql`](db/schema-tier.sql) — 서열표 (`machines` 를 공유)

- `songs` / `charts` — 곡과 채보(모드 + 레벨). `charts` 에 집계 결과 캐시 컬럼 포함
- `players` — 사람 한 명. 로그인해도 여기 한 줄이고, 로그인하지 않은 사람도 여기서 고릅니다.
  `password_hash` 는 아이디/비밀번호로 가입했거나 관리자인 계정만 갖습니다
  (소셜로만 들어온 사람은 NULL — 아래 [계정과 로그인](#계정과-로그인) 참고).
  `nickname_pending` 은 "이름을 아직 본인이 정하지 않았다" 는 표시입니다 — 소셜로 막
  들어온 계정만 켜지고, `/welcome` 에서 답하면 꺼집니다
- `player_identities` — 소셜 신원 `(provider, provider_uid) → player_id`.
  한 사람이 여러 제공자를 연결할 수 있어야 해서 `players` 에 칸을 더하지 않고 따로 둡니다
  ([`db/migrate-008-oauth-identities.sql`](db/migrate-008-oauth-identities.sql))
- `clear_records` — 클리어 기록. **투표 자격의 근거**
- `difficulty_votes` — 체감 난이도 투표
- `tier_grades` / `tier_settings` — 등급 구간표와 임계값 (아래 참고)
- `game_versions` — 기종 안의 버전 (EZ2DJ 6th TRAX …). `charts.version_id` 가
  가리키고, **NULL 이면 버전을 구분하지 않는 게임**입니다 (펌프 · 사볼)
  ([`db/migrate-059-ez2dj-6th-trax-tier.sql`](db/migrate-059-ez2dj-6th-trax-tier.sql))

[`db/schema-community.sql`](db/schema-community.sql) — 제보 · 리뷰 · 채보 평가

- `machine_reports` — 기종 제보 **이벤트 로그** (있어요 / 없어졌어요 / 대기 N명 / 컨디션).
  컨디션 제보만 `cabinet_id` 로 **기체 1대**를 가리킵니다 (나머지는 기종 단위).
  대기 제보만 수명이 지나면 **행이 지워집니다** (아래 참고)
- `machine_live` / `cabinet_condition` — **뷰**. 대기는 수명 안의 제보로, 컨디션은
  등록값까지 종합해 만듭니다 (아래 참고)
- `report_settings` — 제보 유효기간과 자동 반영 임계값
- `arcade_reviews` — 1인 1리뷰. `arcades.rating_avg` / `review_count` 에 집계 캐시
- `chart_comments` — 채보 평가 (코멘트 + 성향 태그)
- `machine_modes` — 게임별 플레이 모드. `charts.mode` 의 `CHECK` 를 대체합니다
  (펌프 S/D/CO, 사볼 NOV/ADV/EXH/MXM — 게임마다 모드 체계가 다름)
- `machine_difficulties` — 한 모드 안에서 곡마다 갈리는 채보 (EZ2DJ 의 N/H).
  `charts.difficulty` 가 가리키고 **NULL 이면 난이도 축이 없는 채보**입니다.
  모드와 다른 축입니다 — 아래 [난이도 축](#난이도-축) 참고
  ([`db/migrate-059-ez2dj-6th-trax-tier.sql`](db/migrate-059-ez2dj-6th-trax-tier.sql))

[`db/schema-board.sql`](db/schema-board.sql) — 커뮤니티 게시판

- `posts` — 글. **`machine_id` 로 게임 탭이 갈립니다** (테이블을 게임마다 나누지 않음)
- `post_comments` / `post_likes` — 댓글, 1인 1추천
- `board_categories` — 말머리. 코드가 아니라 테이블이라 배포 없이 늘릴 수 있습니다

[`db/schema-board-images.sql`](db/schema-board-images.sql) — 첨부 이미지

- `post_images` — `post_id` 가 **NULL 이면 아직 글에 붙지 않은 업로드**입니다
  (이미지는 글보다 먼저 올라갑니다). 게시판에 나중에 추가된 기능이라 파일이
  분리돼 있습니다 — 자세한 이유는 파일 상단 주석 참고

[`db/views.sql`](db/views.sql) — 파생 객체. **서버가 뜰 때마다 다시 적용됩니다**

- `machine_live` — 수명(4시간) 안의 **대기** 제보를 모아 만든 "지금" 상태. **기종 단위**
- `cabinet_condition` — **컨디션 종합**. 등록값 + 제보를 한 덩어리로 평균내
  반올림한 1~5. **기체 단위**

### 스키마가 변할 때 — 세 가지 경로

| 무엇 | 어떻게 |
|---|---|
| **기능 추가** (새 테이블) | `SQL_GROUPS` 에 새 그룹. sentinel 테이블이 없을 때만 적용 |
| **집계식 변경** (뷰) | `views.sql` — 서버가 뜰 때마다 DROP → CREATE |
| **기존 데이터 수정** | `MIGRATION_FILES` — 한 번만 실행하고 `schema_migrations` 에 이력 |

세 번째가 나중에 추가된 이유가 있습니다. 그룹은 "sentinel 이 없으면 만든다"라서 **기능 추가밖에
못 합니다.** 기종 목록을 손보는 것처럼 이미 있는 데이터를 고치는 변경은

- 그룹 파일에 넣으면 → 기존 DB 는 영원히 못 받고,
- sentinel 을 바꾸면 → 그룹 전체가 재적용돼 **사용자가 쓴 글이 지워집니다.**

그래서 적용 이력을 테이블에 남기고 한 번씩만 실행합니다. 각 마이그레이션은
**여러 번 실행해도 결과가 같게** 씁니다 (`ADD COLUMN IF NOT EXISTS`,
`INSERT … ON CONFLICT DO NOTHING`) — 새로 만든 DB 는 시드에 이미 최종 상태가 있어
아무 일도 하지 않고 이력만 남습니다.

[`db/migrate-001-machine-list.sql`](db/migrate-001-machine-list.sql) — 기종 목록 정리
(DJMAX·철권·인형뽑기 제거, EZ2 → EZ2DJ/EZ2AC 분리, `sort_order` 도입)

[`db/migrate-003-queue-ttl.sql`](db/migrate-003-queue-ttl.sql) — 대기 제보 수명 90분 → 6시간,
그리고 표시 필터에서 **실제 삭제**로. 이미 수명이 지난 대기 제보를 한 번 정리합니다

[`db/migrate-011-queue-ttl-4h.sql`](db/migrate-011-queue-ttl-4h.sql) — 대기 제보 수명
6시간 → **4시간**. 현재 값입니다. 수명은 `report_settings.queue_ttl_minutes` 한 곳에
있고 `machine_live` 뷰와 `purgeExpiredQueueReports` 가 함께 읽습니다

[`db/migrate-002-cabinets.sql`](db/migrate-002-cabinets.sql) — 대수 컬럼을 기체 행으로
(`cabinet_count` → `arcade_cabinets`, 컨디션 제보에 `cabinet_id` 추가). 옛 컨디션 값은
그 기종의 모든 기체에 복사하고, 어느 기체였는지 기록이 없는 옛 컨디션 제보는 1호기에
붙입니다 — NULL 로 두면 "최근 컨디션" 이 통째로 비어 버립니다

[`db/migrate-004-admin.sql`](db/migrate-004-admin.sql) — `players` 에 `password_hash` /
`is_admin` 추가. 계정 테이블을 새로 만들지 않은 이유는 파일 상단 주석 참고

[`db/migrate-026-oauth-nickname.sql`](db/migrate-026-oauth-nickname.sql) — `players` 에
`nickname_pending` 추가. 기본값이 FALSE 라 이미 쓰고 있던 계정은 묻지 않습니다
([소셜로 처음 들어오면 닉네임을 묻습니다](#소셜로-처음-들어오면-닉네임을-묻습니다))

[`db/migrate-017-arcade-favorites.sql`](db/migrate-017-arcade-favorites.sql) — 즐겨찾기
테이블. 새 테이블이라 원래는 `SQL_GROUPS` 자리인데, 그러면 기존 DB 는 sentinel 이 없어
받고 새 DB 는 시드까지 받는 두 경로가 생깁니다. 데이터 없는 표 하나뿐이라
`player_identities`(migrate-008) 와 같은 길로 갑니다

## 관리자 권한

로그인은 **선택**입니다. 로그인하지 않으면 제보·리뷰·글이 상단에서 고른 플레이어로
남습니다 ([`lib/use-player.ts`](lib/use-player.ts)). 로그인이 꼭 필요한 건 **아무나 하면
안 되는 일** — 고치는 것과 지우는 것 — 뿐입니다.
(계정을 만드는 쪽은 아래 [계정과 로그인](#계정과-로그인) 참고.)

| 권한 | 누가 |
|---|---|
| 오락실 **등록 / 수정 / 삭제** (이름·주소·좌표·보유 기종·대수) | **관리자만** |
| 제보 **삭제** | **관리자만** |
| 게시글 · 댓글 **삭제** | **본인 또는 관리자** |
| 게시글 **수정** | **본인만** (관리자도 안 됨 — 아래 참고) |
| 제보 (있어요/없어졌어요/대기/컨디션) · 리뷰 · 채보 평가 · 글쓰기 | 누구나 (지금까지와 동일) |

오락실 레코드를 크라우드소싱에서 뺀 이유: 이름·주소·좌표는 한 번 틀리면 지도에서 엉뚱한
곳이 되는데 되돌릴 사람이 없습니다. 반대로 "지금 대기 몇 명"은 틀려도 몇 시간 뒤 사라지고,
있어요/없어졌어요는 서로 다른 제보자 N명이 모여야 반영됩니다 — 크라우드소싱은 그 위에
얹힌 층에서 그대로 굴러갑니다.

> 신규 등록까지 누구나 열고 싶다면 [`app/api/arcades/route.ts`](app/api/arcades/route.ts)
> 의 `POST` 에서 `requireAdmin` 한 줄과, [`components/ArcadeFinder.tsx`](components/ArcadeFinder.tsx)
> 의 `isAdmin ? ... : ...` 한 곳만 걷어내면 됩니다.

게시판은 오락실과 달리 **덮어쓰기가 아니라 덧붙이기**라 누구나 씁니다. 관리자에게 연 건
치우는 쪽뿐입니다 — 글·댓글 **삭제**는 되지만 **수정은 본인만** 입니다. 지우는 것과 달리
고치는 건 남의 이름으로 남는 글의 내용이 바뀌는 일이라, 관리에 필요한 최소한을 넘습니다.

관리자 권한은 **본인 확인을 대체하는 게 아니라 우회합니다**: 일반 사용자 경로는 세션
주인을 작성자로 보고 남의 글은 403 입니다. 관리자만 그 검사를 건너뜁니다. 둘 다 근거는
**세션 쿠키** 하나입니다 ([`lib/auth.ts`](lib/auth.ts) `requirePlayer` · `isAdminRequest`).

`lib/board.ts` 에서 소유자 검사를 없애는 방식이 아니라 `deletePostAsAdmin` /
`deleteCommentAsAdmin` 로 **함수 이름을 나눴습니다**. `deletePost(id, null)` 처럼
"null 이면 검사 안 함" 으로 합치면, 어딘가에서 `playerId` 가 실수로 null 이 되는 순간
조용히 만능 삭제가 됩니다.

### 계정 만들기

계정의 근거는 DB 가 아니라 **환경변수**입니다. 로그인할 때 `players` 에 그 닉네임이 없으면
만들고, 비밀번호가 다르면 갱신합니다 ([`lib/auth.ts`](lib/auth.ts) `ensureAdminAccount`).
해시를 시드에 박으면 비밀번호가 저장소에 남고, 바꾸려면 DB 를 직접 손대야 합니다.

```bash
# .env.local
ADMIN_NICKNAME=관리자           # 생략 시 '관리자'
ADMIN_PASSWORD=바꿀_비밀번호
AUTH_SECRET=...                 # 세션 쿠키 서명 키 (16자 이상)
```

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"   # AUTH_SECRET 생성
```

개발 환경에서는 둘 다 생략할 수 있습니다 — **`관리자` / `admin1234`** 로 로그인되고
서명 키는 개발용 고정 값을 씁니다(경고 로그가 찍힙니다). `NODE_ENV=production` 에서는
`ADMIN_PASSWORD` 가 없으면 로그인이 **503**, `AUTH_SECRET` 이 없으면 에러입니다.

비밀번호를 바꾸려면 `.env.local` 의 `ADMIN_PASSWORD` 만 고치고 다시 로그인하면 됩니다.
계정을 더 만들거나 권한을 회수하려면 `players.is_admin` 을 직접 켜고 끄면 됩니다
(비밀번호가 있어야 로그인되므로 `password_hash` 도 함께 채워야 합니다).

### 어떻게 막나

- **비밀번호** — scrypt (node 기본 제공). `scrypt$<salt>$<key>` 형식이라 나중에
  파라미터를 올려도 옛 해시를 구분할 수 있습니다
- **세션** — 값을 HMAC-SHA256 으로 서명한 httpOnly 쿠키 한 장 (`arcade_session`, 7일).
  세션 테이블을 두면 만료·정리가 따라오는데 담을 게 "누가 관리자인가" 한 줄뿐입니다
- **판정은 서버가** — 화면에서 버튼을 감추는 건 안내일 뿐입니다. 실제 차단은 라우트
  첫 줄의 `requireAdmin` 이고, 쿠키의 `adm` 만 믿지 않고 **DB 를 한 번 더 봅니다**
  (권한을 뗀 계정의 쿠키가 만료까지 통하면 회수가 회수가 아닙니다)
- **시도 제한** — 같은 IP 에서 8회 실패하면 10분. 카운터는 **DB**(`login_failures`,
  db/migrate-052)에 있으므로 프로세스를 여러 개 띄워도 하나로 셉니다. 프로세스
  메모리였던 동안에는 프로세스 수만큼 여유가 생겼고(8프로세스 = 실질 64회),
  재시작하면 풀렸습니다.
  **아직 IP 만 셉니다** — 프록시를 갈아타며 한 계정을 노리는 분산 시도는 못 막고,
  IP 를 공유하는 곳(학교·회사)에서는 무고한 사람이 함께 잠깁니다. 다음 걸음은
  `account:<닉네임>` 키를 하나 더 세는 것입니다(없는 닉네임에도 걸어야 합니다 —
  안 그러면 잠기는지 여부로 계정 존재가 샙니다)

소셜 로그인도 같은 것을 그대로 씁니다 — 바뀌는 건 "무엇으로 본인을 증명했는가"
(비밀번호 → 인가 코드)뿐이고, 세션 발급과 권한 판정은 한 벌입니다.

## 계정과 로그인

들어오는 길은 셋이고, 셋 다 끝나면 **같은 세션 쿠키 한 장**이 됩니다.

| 길 | 화면 | 만들어지는 것 |
|---|---|---|
| 아이디 / 비밀번호 | `/login` | — (이미 있는 계정으로 들어옵니다) |
| 회원가입 | `/signup` | `players` 한 줄 (`password_hash`·`email` 채움, `is_admin` 은 그대로 FALSE) |
| 소셜 (Google · 카카오 · 네이버) | 두 화면의 버튼 | `players` 한 줄 + `player_identities` 한 줄 |

가입은 **아이디와 비밀번호만** 받습니다. 이메일은 받지 않습니다 — 인증 메일도 비밀번호
찾기도 보낼 곳이 없으면, 이메일은 지키기만 해야 하는 개인정보로 남습니다.
가입과 동시에 로그인됩니다(방금 정한 비밀번호를 다시 치게 하는 화면은 아무것도
확인해 주지 않습니다). 아이디는 곧 플레이어 닉네임이라 제보·리뷰·글에 그대로 찍힙니다.

### 소셜 로그인은 어떻게 도는가

셋 다 OAuth 2.0 인가 코드 흐름이라 다른 건 **주소와 프로필 JSON 모양**뿐입니다.
그래서 제공자마다 라우트를 두지 않고 표 하나([`lib/oauth.ts`](lib/oauth.ts) `PROVIDERS`)에
적어 두고 `/api/auth/oauth/[provider]` 한 벌이 셋을 다 처리합니다. 넷째가 붙어도 한 줄입니다.

```
/api/auth/oauth/kakao?next=/community     ← 링크로 이동 (fetch 가 아닙니다)
  → state 쿠키를 심고 카카오 인가 화면으로 302
  → /api/auth/oauth/kakao/callback?code=…&state=…
  → state 대조 → 토큰 교환 → 프로필 조회 → 계정 연결 → 세션 쿠키 → next 로
                                              (처음이면 next 대신 /welcome 으로)
```

- **state** — 콜백이 우리가 보낸 요청의 답인지 아는 유일한 근거입니다. 없으면 남이 만든
  `?code=…` 링크를 누른 사람이 남의 계정으로 로그인됩니다(CSRF). 서명된 쿠키에 담고
  쿠키·값·제공자 세 가지를 모두 봅니다
- **PKCE** — Google·카카오는 `code_challenge`(S256)를 함께 보냅니다. 인가 코드가 새어
  나가도 `code_verifier` 없이는 토큰으로 못 바꿉니다 (네이버는 공식 지원이 없어 끕니다)
- **이메일로 계정을 합치지 않습니다** — 제공자마다 검증 여부가 달라서, 검증하지 않은
  이메일로 합치면 남의 계정을 가져가는 길이 열립니다. 같은 사람이 카카오와 구글로
  각각 들어오면 지금은 서로 다른 계정입니다
- **처음 들어온 사람에게는 이름을 묻습니다** — 제공자 동의·인증이 끝나고 돌아온 자리에서
  `/welcome` 로 한 번 보냅니다 ([아래](#소셜로-처음-들어오면-닉네임을-묻습니다))
- **닉네임이 겹치면 양보합니다** — 제공자 화면에서 곧장 돌아오는 흐름이라 그 자리에서
  실패시키면 되돌릴 방법이 없습니다. 뒤에 숫자를 붙여 두고, 본인에게는 `/welcome` 에서
  다시 묻습니다
- **라이브러리를 쓰지 않는 이유** — 세션이 이미 있습니다. next-auth 를 넣으면 세션·쿠키·
  DB 어댑터가 통째로 따라와 지금 잘 도는 관리자 로그인과 두 벌이 됩니다

### 소셜로 처음 들어오면 닉네임을 묻습니다

아이디/비밀번호로 가입하는 사람은 `/signup` 에서 이름을 고릅니다. 소셜에는 그 화면이
없어서, 예전에는 제공자가 준 이름을 그대로 쓰고 겹치면 뒤에 숫자를 붙였습니다 — 본인이
고른 적 없는 `홍길동2` 가 제보·리뷰·글에 찍혔습니다.

그래서 **동의·인증이 끝나고 우리 쪽으로 돌아온 바로 그 자리**에 한 번 묻습니다.

```
콜백 → 계정 연결 → 세션 쿠키 발급 → /welcome?next=/community   ← 처음 들어온 계정만
                                      ↓ 이름을 정하면
                                    POST /api/auth/nickname → 쿠키 재발급 → next 로
```

- **로그인은 이미 끝나 있습니다** — 세션 쿠키는 `/welcome` 로 보내기 전에 나갑니다.
  여기서 하는 일은 이름을 정하는 것뿐이라 붙잡아 두는 화면이 아닙니다
- **제공자가 준 이름이 미리 채워져 있습니다** — 그대로 쓰려면 그냥 누르면 됩니다.
  "이대로 쓰겠다" 도 본인이 고른 것이라 다음 로그인에 다시 묻지 않습니다
- **건너뛸 수 있습니다** — 나가도 로그인은 그대로입니다. 대신 표시를 끄지 않으므로
  다음 로그인에 다시 묻습니다. 임의로 붙인 이름을 조용히 확정하지 않으려는 것입니다
- **"물어봤는가" 는 DB 에 남깁니다** — `players.nickname_pending`
  ([`db/migrate-026-oauth-nickname.sql`](db/migrate-026-oauth-nickname.sql)). 쿠키는
  사용자가 지울 수 있어 근거가 되지 못하고, 화면을 닫고 나간 사람에게 다시 물어야 합니다
- **기본값이 FALSE 라 이미 쓰고 있던 계정은 묻지 않습니다** — 한동안 그 이름으로 활동했는데
  갑자기 이름을 정하라고 하면 계정이 잘못된 줄 압니다
- **개명 기능이 아닙니다** — 이 라우트는 `nickname_pending` 이 켜진 계정만 통과시킵니다.
  조건을 빼면 비운 이름을 다른 사람이 곧바로 차지해 예전 글의 작성자를 사칭할 수 있습니다

## 실시간 제보는 어떻게 굴러가나

대기 인원은 **5분 뒤에 틀려지는 정보**입니다. 컬럼에 `UPDATE` 로 덮어쓰면 언제 적인지,
몇 명이 같은 말을 했는지가 사라집니다. 그래서 제보는 `machine_reports` 에 **append-only 로
쌓고**, "지금 상태"는 [`machine_live`](db/schema-community.sql) 뷰가 그때그때 만듭니다.

| 종류 | 페이로드 | 단위 | 수명 | 집계 |
|---|---|---|---|---|
| `queue` | 대기 인원 0~99 | 기종 | `queue_ttl_minutes` (4시간) → **행 삭제** | **최대값** |
| `condition` | 컨디션 1~5 | **기체 1대** | `condition_window_days` (**1달**) → 집계에서만 제외 | **등록값과 함께 평균 → 반올림(정수)** |
| `presence` / `absence` | — | 기종 | **없음 (영구)** — 뒤집는 건 시간이 아니라 반대 제보 | 서로 다른 제보자 수 |

- **컨디션은 등록값과 한 덩어리** — 등록 컨디션을 제보 한 건처럼 세어 함께 평균냅니다.
  예전에는 둘이 따로여서 같은 자리에 제보가 있으면 "컨디션 4.7", 없으면
  "등록 컨디션 5/5" 로 **뜻이 다른 두 숫자**가 번갈아 나왔습니다. 결과는 반올림한
  정수입니다 — 1~5 다섯 칸짜리 눈금에 `4.67` 은 있지도 않은 정밀도를 주장합니다.
  대신 몇 건이 모인 값인지(`3건` / `등록값`)를 옆에 적어 신뢰도를 넘깁니다.

- **컨디션만 기체 단위인 이유** — 같은 오락실 같은 게임이라도 1호기는 멀쩡한데 2호기
  발판만 죽어 있는 경우가 흔합니다. 기종 단위로 평균 내면 그 사실이 "컨디션 3.5" 한 줄로
  뭉개집니다. 반대로 **대기는 기종 단위**입니다 — 줄은 게임 앞에 서지 호기별로 서지
  않고, 제보하는 사람에게 몇 호기 줄인지까지 고르게 하면 제보가 흩어져 집계가 서지
  않습니다. 그래서 뷰가 둘로 갈립니다 (`machine_live` / `cabinet_condition`).

- **평균이 아니라 최대값** — 대기 인원은 틀릴 때의 손해가 한쪽으로 기운 값입니다.
  실제보다 적게 알려주면 갔다가 줄 서서 돌아오지만, 많게 알려주면 안 가고 마는
  정도입니다. 그래서 `5명 / 6명 / 4명` 이 엇갈리면 **6명**으로 내보냅니다.
  값이 이미 정수라 반올림도 없습니다 (집계는 뷰에서 — 화면에서 다시 가공하지 않습니다).
  대신 한 명이 장난으로 99 를 넣으면 그대로 99 로 뜹니다. 중앙값이던 시절에는 그런 값이
  묻혔는데, 지금 방어선은 제보자 신원뿐이고 그건 계정에 매달려 있습니다 (아래 참고).
- **만료된 제보는 0 이 아니라 없음** — 수명이 지나면 집계에서 사라지고, UI 는 "지금 대기"
  칸을 아예 그리지 않습니다. `0명` 은 "가면 바로 할 수 있다"는 전혀 다른 주장입니다.

- **세 종류가 서로 다른 속도로 낡습니다** — 대기는 4시간이면 **틀린 값**이 되어 행까지
  지웁니다. 컨디션은 천천히 변하지만 영원하지는 않아 **1달** 창으로 봅니다(행은 남기고
  집계에서만 뺍니다 — 두 달 전 평가가 섞이면 그 사이 정비된 기체가 계속 나쁜 점수를
  답니다. 창을 다시 넓히면 옛 제보가 그대로 되살아납니다). 기종 변동은 **영구**입니다 —
  "이 오락실에 이 게임이 있다" 는 시간이 지난다고 틀린 말이 되지 않고, 그걸 뒤집는 것은
  시간이 아니라 **반대 제보**입니다 (`applyPresence` 는 반대 제보가 마지막으로 들어온
  뒤로만 셉니다). 그래서 전국 피드의 기간 필터에도 **'전체 기간'**(조건 없음)이 있어야
  합니다 — 보존 기간과 조회 기간이 어긋나면 둘 중 하나는 거짓말이 됩니다.
- **대기 제보만 실제로 지웁니다** — 4시간이 지나면 `machine_reports` 에서 행이 사라집니다.
  대기 인원은 되돌아볼 값이 아니라 지나면 그냥 틀린 값이고, 남겨 두면 전국 피드의
  '최근 24시간' 을 채워 방금 올라온 제보를 밀어냅니다. 컨디션·있어요/없어졌어요는
  누적이 근거가 되므로 그대로 둡니다.
  별도 스케줄러가 없어 **제보를 쓸 때와 피드를 읽을 때** 함께 정리합니다
  ([`lib/reports.ts`](lib/reports.ts) `purgeExpiredQueueReports`). 서버가 놀고 있는
  동안에는 남아 있다가 다음 요청에 지워지는데, 그 사이에도 화면에는 안 보입니다 —
  `machine_live` 가 같은 설정값으로 한 번 더 거릅니다. 기준 시각은 앱이 아니라 DB 의
  `now()` 입니다 (두 곳에서 시간을 재면 뷰에는 보이는데 이미 지워진 행이 생깁니다).
- **캐시 컬럼을 두지 않은 이유** — 대기 인원은 아무도 쓰지 않아도 시간이 지나면 무효가
  됩니다. 갱신해 줄 쓰기 시점이 없으므로 뷰가 맞습니다.
- **저장은 숫자, 표시는 구간** — "지금 대기가 많아요"는 드롭다운에서 높은 숫자를 고르는
  것으로 표현됩니다. 문구만 받으면 집계가 안 되고, 숫자만 보여주면 3명이 많은 건지 감이 안 옵니다.
  구간 경계는 UI 문구라서 DB 가 아니라 [`lib/community-types.ts`](lib/community-types.ts)
  의 `WAIT_LEVELS` 에 있습니다.
- **구간은 머릿수가 아니라 `대기 인원 ÷ 기체 대수`** 로 정합니다.

  | 기체당 인원 | 문구 |
  |---|---|
  | 0명 | 바로 가능 |
  | 0명 초과 ~ 2명 미만 | 대기 있음 |
  | **2명 이상** | **보통** |
  | **3명 이상** | **많음** |
  | 4명 이상 | 매우 많음 |

  같은 "6명 대기" 가 1대뿐인 곳에서는 여섯 판을 기다리는 것이고 3대인 곳에서는 두 판
  입니다 — 머릿수로 나누면 기체가 많은 곳이 억울하게 '많음' 이 됩니다. 그리고 경계를
  **낮게** 뒀습니다: 리듬게임은 한 판이 짧지 않고, 앞에 한 명만 있어도 서서 기다리는 일은
  금세 지칩니다. 0명이 아니면 아무리 적어도(3대에 1명 = 0.33) 최소 '대기 있음' 입니다 —
  기다리는 사람이 있는데 '바로 가능' 이라고 말할 수는 없고, 줄이 있는데 '여유' 라고
  부르면 "가면 바로 할 수 있다" 쪽으로 오해합니다.

  대수를 모르는 자리에서는 **1대로 봅니다**(불리하게). 그래서 전국 피드도 대수를 함께
  내려받습니다 (`MachineReport.cabinetCount`) — 같은 제보가 피드에서는 '매우 많음',
  상세에서는 '보통' 으로 갈리면 둘 중 하나는 거짓입니다.

### "이 게임 있어요" 는 승인자 없이 반영됩니다

서로 다른 사람의 제보가 `presence_threshold`(기본 2명) 만큼 모이면
`arcade_machines` 를 자동으로 고칩니다 ([`lib/reports.ts`](lib/reports.ts)).
새로 등록될 때는 **1호기 한 대**를 함께 답니다 — 기체가 0대면 화면에 카드가 없어
컨디션 제보를 받을 자리가 사라집니다. 실제 대수는 오락실 수정에서 늘립니다.

- **세는 구간은 "반대 제보가 마지막으로 들어온 뒤"** — 이게 없으면 3년 전 '있어요' 2건이
  오늘의 '없어졌어요' 를 영구히 이기고, 기종이 빠진 오락실을 지도에서 지울 수 없습니다.
- **익명 제보는 임계값에 세지 않습니다** — 한 사람이 새로고침만 해도 임계값을 채울 수
  있으면 임계값이 아무 의미가 없습니다. 제보 자체는 로그에 남습니다.
- 검수자를 세워야만 굴러가는 구조로 만들면 제보가 쌓여도 지도가 갱신되지 않습니다.
  대신 **모든 근거가 로그에 남아** 있어서, 나중에 되돌리거나 어뷰징을 추적할 수 있습니다.

## 도우미 — 오른쪽 아래 챗봇

화면 오른쪽 아래 떠 있는 아이콘이 앱의 유일한 대화 입구입니다
([`components/ChatBot.tsx`](components/ChatBot.tsx)). 하는 일이 둘로 갈립니다.

| 입력 | 처리 | API 키 |
|---|---|---|
| "내 주변 오락실 찾아줘" | 1·2·3순위를 **드롭다운으로 물어본 뒤** 점수를 매겨 지도·목록에 표시 | 필요 없음 |
| 그 밖의 질문 | 커뮤니티·실시간 제보·웹을 뒤져 답변 | 필요 |

### 탐색은 모델에 맡기지 않습니다

어느 쪽으로 갈지는 [`lib/chat-types.ts`](lib/chat-types.ts) `isArcadeSearchIntent`
가 **말뭉치 규칙으로** 가릅니다. 모델에게 물어보지 않는 이유가 둘입니다.

- 이 갈림길 하나로 다음 화면이 정해집니다(드롭다운이 뜨느냐 마느냐). 같은
  문장에 매번 다른 판단이 나오면 사용자는 **무엇을 해야 폼이 뜨는지 배울 수가
  없습니다.**
- 탐색은 이 앱의 본체입니다. API 키가 없거나 한도를 넘겨도 끝까지 굴러가야 합니다.

장소를 가리키는 말(`오락실`·`아케이드`·`게임센터`)과 행동을 가리키는
말(`찾`·`추천`·`탐색`·`가까운`…)이 **둘 다** 있어야 걸립니다. 한쪽만으로 걸면
"홍대 오락실 대기 어때?"(질문)나 "이 곡 채보 찾아줘"(딴 얘기)까지 끌려옵니다.
규칙과 그 한계는 [`tests/chat-intent.test.ts`](tests/chat-intent.test.ts) 에
문장 단위로 박아 두었습니다 — "오락실 영업시간 알려줘" 가 탐색으로 새는 것은
**알면서 그대로 둔 쪽**입니다(폼이 잘못 떠도 무시하면 되지만, 놓치면 탐색을
시작할 방법이 없어집니다).

### 순위는 1·2·3순위로만 받습니다

드롭다운 세 칸이 전부입니다. 같은 항목을 두 칸에 넣을 수 없게 **이미 고른 것은
다른 칸에서 비활성**됩니다 — 막지 않으면 받아 놓고 나중에 거절해야 합니다.

내부 점수는 **1순위 5점 · 2순위 3점 · 3순위 2점**이고
([`lib/recommend.ts`](lib/recommend.ts) `PRIORITY_POINTS`) **화면에는 나가지
않습니다.**

- 슬라이더와 %를 걷어낸 이유: 저울의 눈금을 보여 주면 "컨디션 63%" 가 무슨
  뜻인지 설명할 자리가 필요해집니다. 정작 사람이 답할 수 있는 질문은
  "뭐가 제일 중요하세요?" 하나입니다.
- 5·3·2 인 이유: 1등과 2등의 간격(2)이 2등과 3등의 간격(1)보다 큽니다. 1순위는
  확실히 이기되 나머지 둘이 뒤집을 여지는 남깁니다. 합이 10 이라 1순위가 딱
  절반이고, **3순위도 20% 는 쥡니다** — 0 으로 두면 "3순위" 가 "안 본다" 와
  같아집니다.
- 제출한 폼은 지우지 않고 **잠급니다**. 대화가 길어져도 "그때 뭘 골랐는지" 가
  그 자리에 남습니다. 마지막 선택은 브라우저에 저장되어 다음 폼의 시작값이
  되지만, **자동으로 탐색을 돌리지는 않습니다**
  ([`lib/use-priority.ts`](lib/use-priority.ts)).

탐색이 끝나면 목록이 추천순으로 바뀌고, 지도의 **상위 3곳 마커에 순위 뱃지**가
붙고, 1위가 열립니다. 그리고 챗봇이 "탐색이 완료되었습니다 … 1위 …" 라고
답합니다. 순위 계산은 부모(ArcadeFinder)가 하고 챗봇은 **말로 할 몫만** 받습니다
— 챗봇이 자기 순위를 따로 매기면 지도와 채팅이 서로 다른 1위를 말하게 됩니다.

### 그 밖의 질문 — 앱 안쪽 먼저, 그다음 웹

[`app/api/chat/route.ts`](app/api/chat/route.ts) 가 Gemini(`gemini-3.7-flash`)에
도구 넷을 쥐여 줍니다.

| 도구 | 무엇을 보나 |
|---|---|
| `search_arcades` | 등록된 오락실 · 보유 기종 · 기체별 컨디션 · 지금 대기 · 영업시간 · 평점 |
| `search_reports` | 실시간 제보 피드 (`/live` 와 같은 소스) |
| `search_posts` | 커뮤니티 게시판 제목·본문 검색 |
| `googleSearch` | 앱 밖의 정보 (신곡, 대회, 기기 소식) — 구글이 서버에서 돌리는 내장 도구 |

- **앱 안쪽 도구는 화면이 쓰는 조회 함수를 그대로 감쌉니다**
  ([`lib/chat-tools.ts`](lib/chat-tools.ts)). 챗봇 전용 SQL 을 따로 쓰면 집계
  규칙이 두 벌이 되어 **챗봇이 말하는 값과 화면에 뜨는 값이 어긋납니다.**
- **"제보가 없다" 를 "상태가 좋다" 로 읽지 않게** 도구 응답에 그 차이를 적어
  보냅니다. 대기 제보는 4시간 뒤 실제로 삭제되므로 없는 것이 기본값입니다.
- **출처는 grounding 메타데이터에서만 뽑습니다.** 답변 본문을 정규식으로 긁으면
  모델이 지어낸 주소까지 출처로 달립니다. 구글 검색의 출처 URL 은 원문 주소가
  아니라 구글의 리디렉트 주소로 옵니다.
- **모델이 3 계열이어야 합니다.** 내장 도구(구글 검색)와 함수 선언을 한 요청에
  같이 무는 건 Gemini 3 부터 되는 일입니다. 2.5 로 내리면 둘 중 하나를 포기해야
  합니다.
- **도구 호출 루프는 직접 돕니다.** JS SDK 는 함수를 대신 실행해 주지 않으므로
  `functionCall` → 실행 → `functionResponse` 왕복을 8번으로 끊습니다. 마지막
  왕복은 `functionCallingConfig.mode = NONE` 으로 도구를 막아 **말로 끝내게**
  합니다 — 그냥 끊으면 도구를 부르다 만 턴이 마지막이 되어 답이 빈 채로 갑니다.
- **모델 턴은 손대지 않고 그대로 되돌려 보냅니다.** 생각 서명
  (`thoughtSignature`)이 빠지면 다음 왕복에서 도구 호출 맥락이 끊깁니다.
- 대화 기록 길이는 [서버에서](lib/validation.ts) 막습니다 — 상한이 없으면 남의
  브라우저에서 수십만 자를 보내 토큰을 태울 수 있습니다.

키가 없으면 이 경로만 503 과 안내 문구를 돌려주고, 탐색은 그대로 됩니다.

```bash
# .env.local
GEMINI_API_KEY=...
```

## 추천 점수는 어떻게 매기나

기준점을 **내 위치에 붙여 두고**, 그 자리에서 갈 만한 곳을 컨디션·대기·거리
세 항목으로 저울질합니다 ([`lib/recommend.ts`](lib/recommend.ts)).

### 기준점은 GPS 를 따라 움직입니다

`getCurrentPosition` 은 그 순간의 좌표 한 번뿐이라, 지하철에서 내려 걸어가는 동안
기준점은 출발한 자리에 남습니다. 그래서 `watchPosition` 으로 붙잡습니다
([`lib/use-live-location.ts`](lib/use-live-location.ts)).

- **조회와 계산을 떼어 놓습니다** — GPS 는 몇 초에 한 번 좌표를 주는데 그때마다
  `/api/arcades` 를 부르면 1분에 수십 번 요청이 나갑니다. 조회는 기준점이 **300m 이상**
  움직였을 때만(`REFETCH_MOVE_KM`), 거리와 순위는 **좌표가 올 때마다** 클라이언트에서
  다시 셉니다. 서버와 같은 식(구면 코사인, R=6371km)을 [`lib/geo.ts`](lib/geo.ts) 에
  두는 이유가 이것입니다 — 두 곳이 어긋나면 "목록엔 1.2km 인데 반경 1km 검색에 걸린다"
  가 됩니다.
- **조회 반경에 여유(500m)를 더합니다** — 조회는 마지막 기준점 기준인데 나는 그 뒤로
  최대 300m 더 가 있을 수 있습니다. 넓게 받아 두고 화면에서 **실제 거리로** 자릅니다.
- **부정확한 좌표는 버립니다** — 실내·지하에서는 추정 오차가 500m~2km 로 튀는데, 그
  좌표로 기준점을 옮기면 옆 동네가 1위로 올라왔다가 다음 좌표에 되돌아옵니다.
  오차 300m 초과는 무시하고(`MAX_ACCURACY_M`), 15m 미만 이동도 새 좌표로 치지 않습니다.
  현재 오차 반경은 화면에 그대로 적습니다 — **오차 200m 짜리 좌표로는 200m 차이의
  순위를 믿을 수 없기** 때문입니다.
- **`TIMEOUT` 에는 추적을 끄지 않습니다** — watch 는 살아 있습니다. 여기서
  `clearWatch` 를 부르면 잠깐 신호가 약했을 뿐인데 추적이 영영 꺼집니다.
- 추적을 끄면 **마지막 좌표가 기준점으로 남습니다**. "그 자리에 서 있는 셈" 이 되므로
  순위는 그대로 쓸 수 있고, 지도의 '내 위치' 마커만 사라집니다.

### 세 항목

| 항목 | 무엇을 보나 | 왜 그렇게 뽑나 |
|---|---|---|
| 기체 컨디션 | 기종마다 **가장 좋은 기체**, 여러 기종이면 그 평균 | 2대 중 1대만 멀쩡하면 사람은 멀쩡한 쪽에서 칩니다. 평균(5·1→3)은 실제 경험보다 낮게 잡습니다 |
| 대기 인원 | 기종 중 **가장 붐비는 쪽**(기체당 인원 기준), 점수는 `WAIT_LEVELS` **구간** 단위 | 고른 기종을 다 하려면 제일 긴 줄을 섭니다. '붐빔' 은 머릿수가 아니라 대수로 나눈 값입니다 — 3대에 6명이 1대에 4명보다 빨리 줄어듭니다. 화면엔 '대기 있음'·'보통' 이 뜨는데 순위만 숫자로 매기면 둘 다 '대기 있음' 인 두 곳이 화면상 근거 없이 갈립니다 |
| 거리 | 기준점에서의 직선 거리 / **검색 반경** | "10km 대비 몇 %" 같은 고정 기준을 쓰면 반경 1km 로 좁혔을 때 점수가 전부 0.9 대로 뭉쳐 순위가 안 움직입니다 |

거리 점수가 **반경 기준**이라는 건 뒤집어 말하면, 반경 30km 로 놓으면 14m 와
1.2km 가 둘 다 "코앞" 이라 거리를 1순위로 놓아도 다른 항목이 순서를 가른다는
뜻입니다. 거리를 실제로 물게 하려면 반경을 좁히세요.

**기종 필터를 걸면 그 기종만 보고 점수를 냅니다** — 안 그러면 "펌프만 찾는데 옆에
있는 태고가 멀쩡해서 1위" 가 됩니다.

### 모르는 항목은 지어내지 않습니다

제보가 아직 없는 항목에는 **중립값(0.5)** 을 줍니다.

- 0 을 주면 "아무도 안 가본 곳" 이 "제보로 최악이 확인된 곳" 과 같아지고,
  1 을 주면 아무도 안 가본 곳이 1위가 됩니다. 둘 다 없는 정보를 지어내는 쪽입니다.
- 대신 **`confidence`** 를 따로 냅니다 — 가중치가 실린 항목 중 실제 근거가 있던 비율입니다.
- 목록에는 항목별 근거를 그대로 펴고, 모르는 항목은 **감추지 않고 "정보 없음" 이라고
  적습니다**(점선 테두리). 감추면 그 자리가 괜찮다는 뜻으로 읽힙니다.
- 그래서 **"대기 0명 확인" 이 "대기 정보 없음" 을 이깁니다**. 확인된 좋은 소식은 추측보다
  세야 제보할 이유가 생깁니다.
- 기준점이 없으면 거리 항목이 통째로 '모름' 이 되고, 챗봇도 목록도 그렇다고 적습니다.

### 순위가 흔들리지 않게

동점은 **점수 → 거리 → 이름** 순으로 가릅니다. 마지막을 이름으로 닫는 이유는 GPS 가
1m 흔들릴 때마다 같은 점수의 두 곳이 자리를 바꾸면 목록이 깜빡이기 때문입니다.
`rankArcades` 는 입력 배열을 건드리지 않습니다.

> **점수 자체는 LLM 이 매기지 않습니다.** 근거가 세 개뿐이고 전부 화면에 있는
> 숫자라, 왜 1위인지 한 줄로 설명할 수 있고 오프라인에서도 즉시 계산됩니다.
> 모델에 맡기면 같은 조건에 매번 다른 순위가 나옵니다. 모델은 **말을 알아듣고
> 앱 밖을 뒤지는 일**만 합니다.

## 지도는 보이는 것만 그립니다 — 실측값

오락실이 1,449곳이 되면서 마커를 전부 얹는 것이 가장 비싼 일이 됐습니다. 지금은
화면 범위(+여백 20%) 안의 것만 그립니다 ([`components/NaverMap.tsx`](components/NaverMap.tsx)
의 `CULL_MARGIN`, 판정은 [`lib/geo.ts`](lib/geo.ts) 의 `inBox`/`padBox`).

Chrome · 1280×720 · 서울 zoom 12 · dev 빌드에서 잰 값입니다 (`performance.memory`,
마커 동기화·`draw()` 직접 계측):

| 앱 켠 직후 | 전부 그리기 | 화면 안만 | 차이 |
|---|---|---|---|
| 마커 | 1,449개 | 337개 | **−77%** |
| DOM 노드(문서 전체) | 7,462 | 1,902 | **−75%** |
| JS 힙 | 23.7 MB | 14.3 MB | **−40%** (−9.4MB) |
| 마커 동기화 (한 번의 블로킹 작업) | 622 ms | 156 ms | **4.0× 빠름** |
| `draw()` 호출 | 1,449회 / 68 ms | 337회 / 20 ms | −77% |
| 강제 스타일·레이아웃 100회 | 6,445 ms | 2,397 ms | **2.7× 빠름** |

마커 1개당 DOM 5노드 · 힙 약 8.6KB 입니다 (같은 세션에서 1,112개를 더 붙여 잰 값:
+5,560 노드 · +9.36MB).

**공짜는 아닙니다.** 시야가 바뀔 때마다 붙이고 떼는 일이 새로 생깁니다:

| 조작 1회 | 전부 그리기 | 화면 안만 |
|---|---|---|
| zoom 12→11 | `draw()` 2,898회 / 59 ms · 동기화 없음 | `draw()` 821회 / 25 ms · 동기화 46 ms (147개 추가) |
| pan 0.05° | 0 ms (지도가 레이어를 통째로 옮긴다) | `draw()` 7회 · 동기화 31 ms (7 추가 · 17 제거) |

즉 **메모리·초기 로드는 크게 줄고, 조작 1회에 30~70ms 의 JS 작업이 생깁니다.**
그 작업은 `idle`(끌기·줌이 멈춘 뒤) 한 번만 돌기 때문에 끄는 동안의 프레임에는
들어가지 않습니다. 622ms 짜리 초기 블로킹(60fps 기준 37프레임)을 없애는 값으로는
남는 거래입니다.

### 메모리를 먹는 건 데이터가 아니라 DOM 입니다

| | 값 |
|---|---|
| 전국 1,449곳 목록 (`/api/arcades`) | JSON **446 KB** · 파싱 후 힙 **0.24 MB** |
| 그 1,449곳을 전부 마커로 그리면 | 힙 **+9.4 MB** · DOM **+5,560 노드** |

데이터를 들고 있는 값이 마커로 그리는 값의 **1/39** 입니다. 그래서 줄일 곳은
"무엇을 받아 두는가" 가 아니라 "무엇을 그리는가" 였습니다. 마커 1개당 DOM 5노드 ·
힙 8.6KB · 합성 레이어 1개(`will-change: transform`)입니다.

### 아직 안 줄인 것 — 서버는 전국을 통째로 내려보냅니다

컬링은 클라이언트 얘기라 다운로드·파싱은 그대로입니다. `/api/arcades` 는 이미
`?lat=&lng=&radius=` 를 받으므로, 지도 화면에 맞춰 부르면:

| 요청 | 크기 | 곳 |
|---|---|---|
| 전체 (지금) | 446 KB | 1,449 |
| 반경 17km (서울 zoom 12 화면과 비슷) | **80 KB** | 248 |
| 반경 5km | 11 KB | 35 |

화면 기준으로 자르면 **−82%** 입니다. 다만 목록 개수 표시("1,449곳 중 30곳")와
챗봇 탐색이 전국 집합을 전제로 하므로, 그 둘을 함께 고쳐야 합니다.
(dev 서버는 React StrictMode 로 이 요청이 2번 나갑니다 — production 은 1번입니다)

### 마커는 떼지 않고 **재활용**합니다

컬링을 켠 뒤 남은 렉의 정체는 마커를 붙였다 떼는 값이었습니다. 실측(349개가 붙은
화면에서 검색으로 142개가 화면 밖으로 나갈 때):

| 한 번의 조작 | 떼고 다시 만들기 | 숨겨 두고 갈아 끼우기 |
|---|---|---|
| 142개 화면 밖으로 | `setMap(null)` **236 ms** (개당 1.66ms) | `display:none` **1 ms** |
| 142개 화면 안으로 | 새로 만들기 **70 ms** (개당 0.49ms) | 갈아 끼우기 **16 ms** |
| 검색 3회 총 블로킹 | 611 ms | **431 ms** |

`naver.maps.OverlayView#setMap(null)` 이 개당 1.66ms 입니다 — 지도를 한 번 움직일
때마다 화면이 0.2초 멈춥니다. 그래서 화면에서 빠진 마커는 **떼지 않고 숨겨 모아
두고**, 새 오락실이 들어오면 그걸 꺼내 좌표·내용만 갈아 끼웁니다. 모아 두는 양은
화면 하나 분량(`MARKER_POOL_MAX = 200`)으로 제한해, 컬링으로 줄인 DOM 이 다시
불어나지 않게 합니다. 남은 431ms 는 마커가 아니라 목록 조회(446 KB)·파싱·렌더 값입니다.

**마커마다 걸어 뒀던 `will-change: transform` 도 걷어냈습니다.** 화면에 337개가 붙으면
합성 레이어가 337개 생기는데, 패닝은 naver 가 마커가 담긴 pane 을 통째로 옮기므로
개별 마커의 transform 은 줌에서만 바뀝니다. 좌표가 계속 바뀌는 '내 위치' 마커만
남겼습니다.

### 선택한 곳은 화면 정중앙

목록에서 고르든 지도 핀을 누르든 그 좌표가 지도 가운데로 옵니다. 두 번에 걸쳐
맞춥니다 — 지금 한 번, 상세 패널이 열리며 지도 칸이 380px 줄어드는 전환(180ms)이
끝난 뒤 한 번 더. 그리고 그 전에 **`map.autoResize()` 로 칸 크기를 다시 잽니다**:
naver 는 창 크기만 지켜보므로 사이드바를 접었다 편 것을 모르고, 그 상태로 `setCenter`
하면 옛 폭의 가운데에 놓아 핀이 **360px 밀립니다**(실측). `refresh()` 는 다시 그리기만
하고 크기를 재지 않아 증상이 그대로였습니다.

> 재는 동안 **헛일 하나를 찾아 지웠습니다.** 시야가 바뀌면 보이는 마커 *전부*의
> HTML 문자열을 다시 만들어 `innerHTML` 에 넣고 있었습니다 — 0.05° 옮길 때 실제로
> 바뀌는 건 24개인데 450개를 다시 그렸습니다. 마커마다 "지금 그려진 근거"(arcade
> 참조 + z)를 들고 있다가 같으면 건너뛰게 바꿨습니다: **동기화 64.6ms → 30.8ms,
> `draw()` 474회 → 7회.**

## 체감 난이도 서열표는 어떻게 계산되나

랭킹(Elo 같은 상대 비교)이 아니라 **게이트된 투표 + 통계 집계**입니다.

1. **투표 자격은 클리어 기록** — 그 채보를 클리어한 사람만 투표할 수 있습니다.
   애플리케이션 검증뿐 아니라 `difficulty_votes` 가 `clear_records` 를 **복합 FK 로 참조**해
   DB 레벨에서 막습니다. 클리어를 해제하면 그 투표도 `ON DELETE CASCADE` 로 함께 사라집니다.
2. **평균값 → 최근접 등급** — 투표 평균과 가장 가까운 `tier_grades.anchor` 로 자동 배치.
3. **수렴도** = `max(0, 1 - 표준편차 / tier_step)` — 투표가 완전히 일치하면 1.0,
   등급 간격만큼 흩어지면 0.0. `min_convergence` 미만이면 **개인차**(체감이 크게 갈리는 채보).
4. **표본 부족** — 투표가 `min_votes` 미만이면 **미정**.

집계는 [`db/schema-tier.sql`](db/schema-tier.sql) 의 `recalc_chart_stats(chart_id)` SQL 함수
하나에 있습니다. 투표가 바뀔 때 그 채보만 재계산하고(가벼움), 결과를 `charts` 의 캐시
컬럼에 써둡니다 — 티어표는 읽기가 압도적으로 많고 쓰기는 드물기 때문입니다.
인자를 `NULL` 로 주면 전체 재계산이라 배치/마이그레이션에도 같은 함수를 씁니다.

> **anchor 값과 임계값은 튜닝 파라미터입니다.** 시드는 '중'을 0 에 둔 좌우 대칭 7단계
> (`최상 1.0 · 상 0.7 · 중상 0.4 · 중 0 … 최하 -1.0`), `min_votes 3`,
> `min_convergence 0.30` 으로 넣어뒀지만
> 검증된 상수가 아닙니다. 코드가 아니라 `tier_settings` / `tier_grades` **테이블**에
> 있으므로 배포 없이 조정할 수 있고, 게임마다 단계 수를 다르게 둘 수 있습니다.

### 게임별 서열표

서열표는 `tier_settings` 가 등록된 게임마다 하나씩 생깁니다. 게임을 붙이려면
**코드가 아니라 데이터만** 넣으면 됩니다.

```sql
INSERT INTO tier_settings (machine_id, vote_min, vote_max, tier_step, min_votes, min_convergence) …
INSERT INTO tier_grades   (machine_id, code, label, anchor, sort_order) …   -- 단계 수는 자유
INSERT INTO machine_modes (machine_id, code, label, sort_order) …           -- 그 게임의 모드
INSERT INTO game_versions (machine_id, code, label, sort_order) …           -- 버전이 있는 게임만
INSERT INTO machine_difficulties (machine_id, code, label, sort_order) …    -- 난이도 축이 있는 게임만
INSERT INTO songs / charts …
```

시드에는 **펌프(7단계, S/D)** 와 **사운드 볼텍스(5단계, EXH/MXM)** 를 넣어 뒀습니다 —
단계 수·투표 범위·모드 이름이 게임마다 다르게 나오는지 확인하기 위한 것입니다.
투표 분포 히스토그램의 열 수도 등급 수에 맞춰 늘어납니다.

### 버전이 있는 게임

EZ2DJ 처럼 한 기종 이름 아래 1st·2nd·…·6th 가 이어지고 **같은 곡의 채보가 버전마다
다른** 게임은, 버전을 구분하지 않으면 6th 의 `Ztar warZ` 와 다른 버전의 `Ztar warZ` 가
한 칸에 섞입니다. 그래서 채보가 `charts.version_id` 로 버전을 답니다
([`migrate-059`](db/migrate-059-ez2dj-6th-trax-tier.sql)).

- `game_versions` 에 행이 있는 게임만 화면에 **버전 선택기**가 생깁니다. 없으면
  (펌프·사볼) 선택기가 아예 그려지지 않고 `version_id` 는 NULL 로 남습니다 —
  난이도 축인 게임에 모드 선택기가 없는 것과 같은 방식입니다.
- 보드를 정하는 단위가 (기종, **버전**, 모드, 레벨) 이 됩니다.
- 기본값은 그 게임의 **첫 버전**(`sort_order = 1`)입니다 — 게임·레벨 선택기가 모두
  "없으면 첫 항목" 이라 같은 규칙으로 뒀습니다.

지금 등록된 것은 **EZ2DJ 의 두 버전**이고, 둘 다 투표를 넣지 않아 전부 '미정' 에서
시작합니다. 모드는 7개로 같습니다 (Ruby · 5 Street · 7 Street · Club · Space ·
Catch · Turn).

| 버전 | 곡 | 채보 | 난이도 |
|---|---:|---:|---|
| 6th TRAX ~Self Evolution~ ([059](db/migrate-059-ez2dj-6th-trax-tier.sql)) | 138 | 837 | N · H |
| 7th TRAX ~Resistance~ ([060](db/migrate-060-ez2dj-7th-trax-tier.sql)) | 170 | 1,080 | E · N · H · S |

두 버전이 곡을 공유합니다 — `songs` 는 한 벌(170곡)이고 `charts` 만 버전별로 붙습니다.
7th 문서가 같은 곡을 다르게 적은 것이 50곡이라(`Dieoxin`/`DIEOXIN`, `1234`/`One Two
Three Four`) 060 이 별칭 표로 이어 붙입니다 — 안 하면 songs 가 두 줄이 됩니다.

### 레벨을 모르는 채보

출처가 난이도 칸을 `?` 로 비워 둔 채보가 셋 있습니다(Space H 의 `Look Out` ·
`Dieoxin` · `Frantic`). **채보는 있는데 난이도만 모르는 것**이라 빼지도 지어내지도
않고 `charts.level` 을 NULL 로 둡니다.

- 레벨 선택기에 `Lv.?` 칸이 하나 생기고 거기 모입니다 (제목은 `Space Lv.?`). 주소에서는
  `?level=unknown` 입니다 (`UNKNOWN_LEVEL` — 숫자 자리에 물음표를 넣으면 파서가
  흔들립니다).
- 보드 조회가 `c.level = $4` 가 아니라 `IS NOT DISTINCT FROM` 인 이유가 이것입니다 —
  `= NULL` 은 아무것도 고르지 못합니다.
- 같은 이유로 `charts.level` 의 상한이 30 → **99** 입니다. `Theme of Ez2Dj` 의 히든
  채보가 그 게임에서 실제로 **99** 로 표시됩니다.

### 난이도 축

**모드와 난이도는 다른 축입니다.** 모드는 *무엇을 플레이하는가*(Ruby · Club · Space…)고,
난이도는 *같은 곡의 어느 채보인가*(EZ · NM · HD · SHD)입니다. EZ2DJ 는 둘 다 있는 첫 게임입니다.

- 보드는 여전히 **(모드, 레벨)** 로 정해지고, 난이도는 사볼처럼 곡명 뒤 대괄호로만
  보입니다 (`Weird Wave [HD]`). 같은 레벨이면 NM 이든 HD 든 **한 표에서 비교해야**
  하기 때문입니다 — 근거는 [`migrate-045`](db/migrate-045-mode-is-difficulty.sql).
- 그래서 `UNIQUE` 가 `(song_id, version_id, mode, difficulty, level)` 입니다. 난이도를
  빼면 `Complex` 의 Space NM 10 과 HD 10 처럼 **레벨까지 같은 두 채보**가 조용히
  사라집니다 (`ON CONFLICT DO NOTHING` 이라 오류도 안 납니다).
- **사볼은 이 컬럼을 쓰지 않습니다.** 모드 축이 아예 없어서 난이도를 `charts.mode` 에
  담고 `tier_settings.mode_is_difficulty` 로 구분하는 지름길을 씁니다(045). 두 방법이
  공존하는 셈이라, 언젠가 사볼을 `difficulty` 로 옮기면 하나로 줄일 수 있습니다.

> ⚠ 게임을 바꾸면 이전 게임의 (모드, 레벨) 이 그대로 넘어옵니다 (펌프 S1 → 사볼 S1).
> `/api/tier` 는 mode/level 을 **희망값**으로 받아 없는 조합이면 가장 가까운 조합으로
> 대신 그리고, 실제로 그려진 조합을 `board.mode` / `board.level` 로 돌려줍니다.
> 화면은 그 값만 신뢰합니다 — 요청값과 결과값을 양쪽에 두면 둘이 어긋납니다.

### 채보 평가 — 숫자 옆의 문장

서열표의 등급만 보고 골랐다가 막히는 건 대개 **왜 어려운지**를 모르기 때문입니다
(틀기 약한 사람에게 틀기 채보, 체력 없는 사람에게 롱런). 투표(스칼라 1개)와 분리해
`chart_comments` 에 코멘트 + 성향 태그를 답니다.

- **태그는 고정 목록** ([`CHART_TAGS`](lib/community-types.ts)) — 자유 입력으로 두면
  '폭타' / '폭타패턴' / '폭타형' 이 각각 쌓여 집계가 불가능해집니다.
- **고를 수 있는 태그는 게임마다 다릅니다** (`CHART_TAGS_BY_MACHINE`) — 무엇으로
  어려운지가 게임마다 달라서입니다. 펌프는 발판(떨기·틀기·겹발·체중이동·체력), 사볼은
  손(지력·건반·노브·트릴), EZ2AC·EZ2DJ 는 거기에 턴테이블과 발이 더 붙습니다
  (**트릴·스크래치·페달·겹놋**). 등록되지 않은 게임은 공통 태그 8개만 나옵니다.
  저장 검증은 **합집합**(`CHART_TAGS`)으로 합니다 — 게임별로 좁히면 목록을 손볼 때마다
  이미 저장된 평가를 그 작성자가 수정할 수 없게 됩니다.
- **태그 줄은 한 줄에 두고 옆으로 밉니다** (`ScrollStrip` — 커뮤니티 게임 탭과 같은
  부품). 접히게 두면 게임마다 태그 수가 달라 그 아래 입력란이 오르내립니다.
- **클리어 게이트가 없습니다** — 못 깬 사람의 "여기서 막힌다" 도 정보입니다. 대신 목록에
  **클리어 / 미클리어** 배지를 함께 실어 읽는 쪽이 가중치를 판단합니다.
- **투표값은 평가에 붙이지 않습니다** — 투표 분포를 익명으로 두기로 한 결정이 평가란을
  통해 뚫리면 안 되기 때문입니다. 클리어 여부만 나갑니다.

## 커뮤니티 — 게임별 탭은 테이블이 아니라 컬럼입니다

`/community` 는 리듬게임마다 탭이 하나씩 있는 게시판입니다. 탭은 `machines` 에서
`category = 'rhythm'` 인 기종 목록이고, 글은 `posts.machine_id` 로 갈립니다.

**"펌프 게시판" 테이블을 따로 만들지 않은 이유**

- '전체' 탭이 10-way `UNION` 이 됩니다. 지금은 `machine_id` 조건을 빼면 끝입니다.
- 게임을 하나 붙일 때마다 마이그레이션이 필요합니다. 지금은 `machines` 에 행 하나만
  넣으면 탭이 생깁니다 — 서열표(`tier_settings`)와 같은 방식입니다.
- 정렬·페이지네이션·말머리 필터를 게시판 수만큼 복제해야 합니다.

**글이 0건인 게임도 탭에 남깁니다** — 글이 있는 게임만 보여주면 새 게임에 첫 글을 쓸
방법이 없어집니다. 탭 옆 숫자가 0이면 "여기 첫 글을 써라"는 안내입니다.

**집계 캐시** — 목록은 글 20건마다 댓글/추천 수를 함께 보여줍니다. 매번 `COUNT` 를
돌리면 목록 조회가 글 수 × 2번의 집계가 되므로, `charts.vote_count` 와 같은 방식으로
`posts.comment_count` / `like_count` 에 캐시하고 `recalc_post_stats(post_id)` 로
그 글만 갱신합니다.

**추천은 토글 하나** — 켜기/끄기 두 엔드포인트로 나누면 클라이언트가 현재 상태를 알아야
하고, 그 상태가 틀리면(다른 탭에서 이미 눌렀다면) 조용히 어긋납니다. `POST .../like` 는
DB 의 현재 상태를 보고 뒤집습니다. `post_likes` 에 `(post_id, player_id)` PK 가 있어서
같은 사람이 반복 추천할 수 없고, "내가 이미 추천했는지"도 그걸로 표시합니다.

**조회수** — `?view=1` 이 붙은 조회에서만 올립니다. 상세를 열 때만 붙이고 추천·댓글 후
재조회에는 붙이지 않습니다. 조회 로그를 남기지 않으므로 새로고침 반복은 막지 못합니다 —
막으려면 (글, 사람, 시각)을 저장해야 하고, 그건 이 값의 용도(목록에서 대충 눈에 띄는
순서)에 비해 과합니다.
⚠ dev 서버는 React Strict Mode 로 effect 를 두 번 실행하므로 개발 중에는 2씩 오릅니다.

**본문은 마크다운을 렌더하지 않습니다** — 사용자가 쓴 줄바꿈만 `white-space: pre-wrap`
으로 살립니다. HTML 을 해석하지 않으므로 XSS 경로가 없습니다. 이미지는 본문 안
마커 위치에 들어갑니다 (아래 참고).

### 페이지네이션 — 글 20개 / 댓글 10개

둘 다 `LIMIT`/`OFFSET` 서버 페이지네이션이고 화면은
[`components/Pagination.tsx`](components/Pagination.tsx) 를 공유합니다. 한쪽만
'더 보기', 다른 쪽은 번호식이면 같은 화면에서 규칙이 두 개가 됩니다.

- **댓글도 서버에서 자릅니다** — `getPost` 가 `commentOffset` 부터 10개만 싣습니다.
  전체 개수는 캐시 컬럼(`comment_count`)에 있어서 화면이 페이지 수를 계산할 수
  있으므로, 댓글 500개짜리 글이 500개를 다 내려보낼 이유가 없습니다.
- **댓글은 오래된 것부터** — 대화가 위에서 아래로 읽혀야 하고, 새 댓글이 항상
  마지막 페이지에 붙습니다. 그래서 댓글을 쓰면 서버가 **마지막 페이지를 담아**
  응답합니다. 1페이지를 보던 사용자에게 1페이지를 돌려주면 방금 쓴 댓글이 화면에
  없어서 등록이 안 된 줄 압니다.
- **추천·댓글 삭제는 보던 페이지를 유지합니다** — 두 엔드포인트가 `commentOffset`
  을 받습니다. 추천을 눌렀다고 댓글이 1페이지로 튀면 안 됩니다.
- **범위를 벗어난 offset 은 서버가 당깁니다** — 마지막 댓글을 지워 그 페이지가
  비면 마지막 페이지로 맞추고, 실제로 쓰인 값을 `post.commentOffset` 으로 돌려줍니다.
  화면은 그 값만 신뢰합니다.
- 글 목록도 같은 이유로, 마지막 페이지의 마지막 글을 지우면 한 페이지 물러납니다.

### 이미지 — 본문 안 원하는 위치에

글쓰기는 `contenteditable` 편집기입니다 ([`PostBodyEditor.tsx`](components/PostBodyEditor.tsx)).
커서 위치에 이미지가 들어가고, 붙여넣기·드래그로도 올라갑니다. 넣은 이미지는 **끌어서
위치를 옮길 수 있고**(복사가 아니라 이동 — 원래 자리에서 사라집니다), 끄는 동안
**어디에 들어갈지 캐럿으로 표시**됩니다.

**그런데 HTML 을 저장하지 않습니다.** 저장할 때 DOM 을 훑어 **평문 + `[[image:12]]` 마커**로
직렬화합니다 ([`lib/board-content.ts`](lib/board-content.ts)):

```
첫째 문단입니다.
[[image:12]]
이미지 아래 둘째 문단입니다.
```

HTML 을 그대로 DB 에 넣으면 (1) 출력마다 sanitizer 를 통과시켜야 하고 그건 계속
구멍이 나는 표면이며, (2) 본문 검색·미리보기가 태그를 걸러내야 하고, (3) 편집기를
바꿀 때 과거 글의 마크업이 발목을 잡습니다. 마커 방식은 저장물이 사람이 읽을 수 있는
텍스트이고, 렌더링은 React 가 텍스트 노드로 넣으므로 XSS 경로가 아예 없습니다.

- **마커가 붙는 이미지의 유일한 근거입니다** — `imageIds` 를 따로 받지 않습니다. 목록을
  같이 받으면 본문과 어긋날 수 있고(본문에서 지웠는데 목록엔 남는 등) 무엇을 믿을지
  정해야 하는 문제가 생깁니다. 본문에서 이미지를 지우면 마커가 사라지므로 자동 분리됩니다.
- **사용자가 마커를 직접 타이핑해도 안전합니다** — 그 글에 실제로 붙어 있는 이미지가
  아니면 렌더러가 **텍스트로** 보여줍니다. 남의 이미지를 본문에 끌어오는 것도 그래서 막힙니다.
- **직렬화 → 복원 → 직렬화가 같은 값이어야 합니다** — 복원할 때 이미지 뒤에 `<br>` 을
  덧붙이면 수정할 때마다 빈 줄이 한 줄씩 늘어납니다. (실제로 그 버그를 만들고 고쳤습니다.)
- **React 가 편집 영역을 다시 그리지 않습니다** — contenteditable 을 controlled 로
  만들면 매 입력마다 캐럿이 맨 앞으로 튑니다. 초기화는 mount 시 1회뿐이고, 이후 내용의
  주인은 DOM 입니다. 부모에게는 직렬화된 문자열만 흘려보냅니다.
- **붙여넣기는 평문화합니다** — 어차피 저장할 때 서식이 버려지므로, 붙여넣는 순간부터
  평문으로 넣어 편집 중 보이는 것과 저장물을 맞춥니다.
- **이미지 드래그 이동은 직접 처리합니다** — `drop` 에서 `preventDefault()` 를 하지
  않으면 브라우저가 자기 방식으로 한 번 더 넣어서 **원본이 그대로 남습니다**(복사처럼
  보임). 넣고 나서 원본을 지우는 순서도 중요합니다 — 먼저 지우면 드롭 위치를 가리키던
  `Range` 의 오프셋이 밀려 엉뚱한 곳에 들어갑니다.
  편집기 밖이나 제자리에 떨어뜨리면 아무것도 하지 않습니다.
- **드롭될 자리를 캐럿으로 표시합니다** — 표시용 노드를 편집 영역 **안에** 넣으면 본문의
  일부가 되어 직렬화에 섞이고, 삽입·제거가 레이아웃을 흔들어 드롭 위치 계산이 어긋납니다.
  그래서 편집 영역을 감싼 상자(`.editor-shell`)에 **겹쳐 그립니다**.
  - 위치는 `caretFromPoint` 로 얻은 Range 의 화면 좌표입니다. 단, 요소 컨테이너에 접힌
    Range(이미지와 `<br>` 사이 등)는 `getClientRects()` 가 **전부 0 인 사각형**을 주므로
    이웃 노드로 추정하는 우회가 필요합니다 — 없으면 캐럿이 편집기 왼쪽 위에 붙습니다.
  - **옮겨도 제자리인 드롭은 표시하지 않습니다.** `caretFromPoint` 는 이미지 위에서도
    그 이미지의 *부모*를 컨테이너로 주므로, `startContainer === 끌던 이미지` 만으로는
    자기 위에 떨어뜨린 경우를 못 잡습니다. 캐럿이 그 이미지의 바로 앞/뒤를 가리키는지도
    함께 봅니다 (`isNoopMove`).
  - `dragover` 는 초당 수십 번 뜨므로 위치가 실제로 1px 이상 움직였을 때만 다시 그립니다.
- **`dragover` 에서 파일 여부는 `dataTransfer.types` 로 봅니다** — 그 시점의
  `dataTransfer.files` 는 보안상 항상 비어 있습니다. files 로 판단하면
  `preventDefault()` 가 걸리지 않아 밖에서 끌어온 이미지 드롭이 조용히 무시됩니다.
- **`loading="lazy"` 를 쓰지 않습니다** — 원본 크기를 저장하지 않아 `width`/`height` 를
  줄 수 없고, 로드 전 `<img>` 는 테두리만 남은 2x2 상자로 찌그러집니다. 그 상태의
  요소는 크롬의 지연 로딩 판단에 걸리지 않아 **화면 안에 있어도 영원히 로드되지
  않습니다.** 글당 5장뿐이므로 즉시 로드합니다.

업로드 자체는 글보다 먼저 일어납니다 — 작성 중에 `POST /api/uploads` 로 한 장씩 올려
그 자리에 미리보기를 띄우고, 저장할 때 본문의 마커로 어느 글에 붙일지가 정해집니다.

- **형식은 매직 바이트로 확인합니다** — 확장자와 `Content-Type` 은 클라이언트가 보내는
  값이라 못 믿습니다. `.png` 로 이름만 바꾼 파일은 **415** 로 거절됩니다.
- **크기는 두 번 봅니다** — `file.size` 로 먼저 거르고(413), 버퍼에서 다시 확인합니다.
  5MB 제한인데 500MB 를 메모리에 다 읽고 나서 거절하면 제한이 방어가 아닙니다.
- **파일명은 내용 해시(SHA-256)** — 같은 이미지를 여러 사람이 올려도 파일은 하나이고,
  같은 id 의 내용이 절대 바뀌지 않으므로 `immutable` 로 영구 캐시할 수 있습니다.
- **`public/` 이 아니라 `/api/uploads/:id`** — 비공개 게시판이나 신고 숨김이 생기면
  그 한 곳에 조건을 넣으면 됩니다.
- **남의 업로드는 붙지 않습니다** — 첨부할 때 `player_id = 올린 사람` 을 함께 확인합니다.
  이 조건이 없으면 남이 올린 이미지의 id 를 넣어 자기 글로 끌어올 수 있습니다.
- **글 저장과 이미지 연결은 한 트랜잭션** — 따로 하면 "글은 있는데 이미지가 안 붙은"
  상태가 남고 사용자는 이미지를 다시 올려야 합니다.
- **본문에서 지우면 삭제가 아니라 분리** — `post_id` 를 NULL 로 되돌립니다. 다시 붙일
  수도 있고, 파일과 행을 함께 정리하는 배치를 나중에 붙이는 쪽이 낫습니다.
  ⚠ **그 배치가 아직 없습니다** — 작성하다 그만두면 고아 행이 남습니다.
  `post_images_orphan_idx` 가 그걸 찾기 위한 인덱스입니다.
- **마커 없이 붙어 있는 이미지는 본문 뒤에 그립니다** — 인라인 배치 이전에 쓰인 글
  (이미지가 본문 아래에 뭉쳐 붙던 방식)이 그렇습니다. 안 그리면 사용자는 이미지가
  사라진 줄 압니다.

| 메서드 | 경로 | 설명 |
|---|---|---|
| `POST` | `/api/auth/login` | 로그인 `{nickname, password}` → `{user}` + 세션 쿠키. 실패 **401**(이유는 한 문장으로 통일), 시도 초과 **429**, `ADMIN_PASSWORD` 미설정 **503** |
| `POST` | `/api/auth/signup` | 회원가입 `{nickname, email, password, passwordConfirm}` → **201** `{user}` + 세션 쿠키, 그리고 **인증 메일 한 통**(응답 뒤에 `after()` 로 — 메일이 늦어도 가입은 늦지 않음). 이메일은 소셜이 아닌 가입에만 있고 필수(소문자로 맞춰 저장). 중복 아이디·**확인된** 중복 이메일 **409**(구분해 안내), 형식 오류 **400**, 시도 초과 **429** |

| `GET` | `/api/auth/verify/resend` | 내 이메일이 확인됐나 `{email, verified, mailConfigured}`. 비로그인 **401** |
| `POST` | `/api/auth/verify/resend` | 인증 메일 다시 보내기(세션 주인의 주소로만). 분당 1회·시간당 5회 **429**, 이미 확인·이메일 없음 **409**, 발송 실패 **502** |
| `POST` | `/api/auth/logout` | 세션 쿠키 삭제 |
| `GET` | `/api/auth/session` | 지금 로그인한 사람 `{user}` (없으면 `{user: null}`). 화면이 관리자 버튼을 그릴지 정하는 근거 |
| `GET` | `/api/auth/oauth/:provider?next=` | 소셜 로그인 시작 — state 쿠키를 심고 제공자로 **302**. 키 미설정이면 `/login?error=unconfigured` 로 되돌립니다 |
| `GET` | `/api/auth/oauth/:provider/callback` | 제공자가 돌려보내는 자리. 성공하면 세션 쿠키 + `next` 로(**처음 들어온 계정은 `/welcome`**), 실패하면 `/login?error=…` 로 **302** |
| `GET` | `/api/auth/nickname` | 소셜 첫 진입인가 — `{nickname, pending}`. 비로그인 **401** |
| `POST` | `/api/auth/nickname` | 닉네임 확정 `{nickname}` → `{user}` + **세션 쿠키 재발급**(쿠키에 이름이 박혀 있습니다). 중복·예약어·이미 정해진 계정 **409**, 형식 오류 **400**, 비로그인 **401** |

> **아래 표에 `playerId` 가 없는 이유** — "누가 하는가" 는 요청이 아니라 **세션 쿠키**가
> 정합니다 ([`lib/auth.ts`](lib/auth.ts) `requirePlayer`). 이름이 붙는 쓰기는 비로그인이면
> **401** 이고, 본문이나 쿼리스트링에 `playerId` 를 섞어 보내도 스키마가 받지 않습니다.
> 개인화되는 읽기(내 추천 여부, 내 클리어)도 같은 근거입니다. **예외는 제보 하나** —
> 지나가다 본 것을 알려주는 자리라 로그인을 요구하지 않고, 익명은 자동 반영 임계값에
> 세지 않습니다.

([`lib/pg-errors.ts`](lib/pg-errors.ts)) — 값 검증을 DB 제약에 맡긴 곳에서 500 이
나가지 않게 하기 위해서입니다.

입력 검증은 [`lib/validation.ts`](lib/validation.ts) 의 zod 스키마 한 곳에서 처리하고,
실패 시 `400` 과 함께 필드별 한글 메시지를 돌려줍니다.

```bash
curl "http://localhost:3000/api/arcades?machines=1,3&lat=37.5665&lng=126.978&radius=10"
```

## 구현 범위

**되는 것**

- 오락실 등록 / 수정 / 삭제 (**관리자만** — [위](#관리자-권한) 참고) / 목록
- 지도 클릭으로 좌표 지정 (또는 위경도 직접 입력)
- 보유 기종 태깅 — 대수를 정하면 **그만큼 호기별 컨디션(1~5) 칸**이 생김
- 기종 AND 필터 (선택한 기종을 *모두* 보유한 곳만)
- 이름/주소 검색, 브라우저 위치 기반 반경 검색 + 거리순 정렬
- **GPS 추적 기준점** — 걸어가면 기준점·반경 원·거리·순위가 함께 따라옵니다.
  조회는 300m 이상 움직였을 때만, 계산은 좌표가 올 때마다 ([위](#추천--지금-어디로-갈까-를-점수-하나로))
- **오른쪽 아래 떠 있는 도우미(챗봇)** — "오락실 찾아줘" 라고 하면 1·2·3순위를
  드롭다운으로 물어보고, 다 고르면 점수를 매겨 지도·목록에 표시한 뒤 완료를 알립니다.
  그 밖의 질문은 커뮤니티·실시간 제보·웹에서 찾아 답합니다
  ([위](#도우미--오른쪽-아래-챗봇))
- **추천순 정렬** — 점수(0~100)와 항목별 근거를 행마다 표시. 지도에는 상위 3곳에
  순위 뱃지
- **지도는 지금 보이는 범위(+여백 20%)의 마커만 그립니다** — 전국 1,449곳을 다
  얹으면 서울만 보고 있어도 부산·제주 마커가 DOM 에 남습니다. 끌거나 줌해서
  화면에 들어오는 순간 그려집니다(`idle` 이벤트 기준 — 끄는 중에 프레임마다
  다시 붙이지 않습니다). 실측: 서울 zoom 12 에서 1,449곳 중 337개, 두 칸 확대하면 47개.
  대체 뷰(키 없을 때)도 같은 규칙입니다 — 기본 시야를 한 도시(0.3° ≈ 33km)로 잡고
  끌기·휠로 옮겨 봅니다
- 마커 ↔ 목록 양방향 선택 연동 — 지도는 화면 안 전부를 그리므로 지금 페이지에
  없는 핀을 누르는 일이 흔한데, 그때는 그 줄이 있는 페이지로 넘어갑니다
- 오락실 선택 → 상세 패널 (기종별 현재 상태 · 제보 · 리뷰)
- 목록 행에 평점과 **지금 대기** 요약 표시. 기종 뱃지의 **컨디션 점은 기체마다 하나** —
  2대인데 한 대만 빨간 점이면 목록에서 바로 보입니다
- **사이드바 목록은 10곳씩 3페이지(최대 30곳)** — 검색어 하나에 250곳이 걸리는데
  32페이지를 넘겨 가며 고르는 사람은 없습니다. 잘렸을 때는 머리글이 분모를 함께
  적습니다 (`250곳 중 30곳 · 가까운 순`). 지도는 자르지 않습니다
- **앱을 켜면 사이드바는 접혀 있습니다** — 아무것도 검색하지 않은 첫 화면에서
  목록이 할 수 있는 말은 몇 줄뿐이라, 그 몇 줄 때문에 지도를 좁혀 두지 않습니다.
  펼치는 손잡이는 접어도 같은 자리에 남습니다
- **사이드바 목록 = 지도에 지금 보이는 곳** — 지도가 그리는 범위를 그대로 받아
  (`MapPane onViewportChange`) 목록을 좁힙니다. 지도와 **같은 박스**로 판정하므로
  "지도에는 있는데 목록에는 없는" 줄이 생기지 않습니다. 머리글이 그 사실을 적습니다
  (`화면 안 248곳 중 30곳 · 가까운 순`)
- **순서** — **선택한 곳**이 맨 위, 그다음 즐겨찾기, 그다음은 챗봇 탐색을 했으면
  추천순 · 내 위치가 있으면 가까운 순 · 둘 다 아니면 평점 높은 순입니다. 선택한 곳을
  즐겨찾기보다 위에 두는 이유: 지금 상세 패널에 열려 있는 그 한 곳이라 목록에서 바로
  짚여야 하고, 즐겨찾기가 여러 곳이면 그 아래로 밀려 페이지 어딘가에 섞입니다. 거리를 모르는데 '가까운 순'
  이라고 적거나 이름 첫 글자가 순위인 척하는 목록을 만들지 않기 위해서입니다
- **화면 밖은 화면 밖이라고 말합니다** — 검색 결과가 있는데 전부 화면 밖이면
  목록은 비고 대신 `조건에 맞는 89곳이 지금 화면 밖에 있습니다` 가 붙습니다.
  검색은 됐는데 목록이 비어 보이는 상태를 그냥 두면 막다른 화면이 됩니다
- **즐겨찾기(★)** — 목록 행과 상세 패널에서 담고 뺍니다. 계정에 붙는 값이라
  로그인해야 별이 뜹니다 (판정은 서버가 세션으로 합니다). 담아 둔 곳은 목록
  맨 위로 옵니다 — 단 **화면 안에 있을 때만** 입니다 (목록이 곧 지도라는 규칙이 먼저)

**제보 · 리뷰**

- 제보 4종 — 있어요 / 없어졌어요 / 지금 대기 N명 / 컨디션 1~5 (+ 한 줄 메모)
- **같은 게임이 2대 이상이면 상세 패널에서 기체 수만큼 카드가 갈리고, 컨디션은
  카드마다 따로 답니다** (1호기 · 2호기). 대기 제보와 '없어졌어요' 는 기종 헤더에
  한 번만 — 줄은 게임 앞에 서고, 기종이 빠지는 건 기체 한 대의 일이 아닙니다
- 대기 인원은 **드롭다운(없음 · 1명 ~ 12명 · 12명+)** 에서 고릅니다. 처음에는
  0·1·2·3·5·8 버튼이었는데 4명·6명·7명 같은 사이값을 고를 수가 없었습니다.
  상한은 [`lib/community-types.ts`](lib/community-types.ts) 의 `WAIT_MAX` 하나로
  정해집니다 (DB 는 0~99 까지 받습니다).
  **상한값 자체를 "이상" 으로 쓰지 않습니다** — 그러면 정확히 12명인 줄을 12명이라고
  말할 수단이 없어집니다. 대신 `WAIT_OVER`(= `WAIT_MAX + 1`)를 "초과" 센티넬로
  저장하고, 표시할 때만 `12명+` 로 읽습니다. 그 위의 값(14~99)은 API 로만 들어오며
  숫자 그대로 보여줍니다 — 장난 제보(99명)를 `12명+` 로 뭉개면 어뷰징이 안 보입니다
- 대기·컨디션 **모두 고른 뒤 메모를 쓰고 등록** — 고르는 순간 전송하면 그 아래 메모 칸에
  뭘 쓸 기회가 없고, 드롭다운은 목록을 훑다 스친 값이 그대로 제보가 됩니다
- 컨디션은 **등록값 + 제보를 종합한 반올림 정수 하나**로 표시 (`컨디션 4/5 · 2건`).
  제보가 아직 없으면 `등록값` 이라고 적고, 등록값도 제보도 없을 때만 "정보 없음"
- 대기 제보는 **4시간이 지나면 자동으로 삭제** — 피드에서도 사라집니다
- 제보 즉시 `machine_live`/`cabinet_condition` 재집계 → 상세·목록·피드가 같은 응답으로 함께 갱신
- 있어요/없어졌어요는 서로 다른 제보자 2명이 모이면 보유 기종에 **자동 반영**
  (익명 제보는 임계값에 세지 않음)
- 오락실 리뷰 1인 1건 — 별점 + 본문, 수정·삭제, 평점 캐시 즉시 재계산
- `/live` 전국 피드 — 종류·기종·기간 필터, 30초 자동 갱신, 오락실로 딥링크
- **관리자 로그인 시 제보마다 삭제 버튼** — 전국 피드와 오락실 상세 양쪽에.
  장난 제보나 메모에 섞인 개인정보를 치우는 유일한 경로입니다 (제보에는 수정이 없습니다)

**서열표 · 채보 평가 (`/tier`)**

- **게임 전환** (펌프 / 사볼 / EZ2DJ) — 등급 단계 수·투표 범위·모드 이름이 게임마다 다름
- 버전 · 모드 · 레벨 전환, 등급별 서열 보드 (게임 등급 수 + 개인차 + 미정).
  버전·모드 선택기는 그 축이 있는 게임에만 그려집니다
- 채보 상세 — 평균/투표수/수렴도, 등급별 투표 분포 히스토그램
- 클리어 기록 등록·해제, 체감 난이도 투표·수정·취소
- 투표 시 해당 채보만 즉시 재집계 → 등급이 실시간으로 이동
- 클리어 게이트: 미클리어 투표는 403, DB 제약으로도 차단
- **채보 평가** — 코멘트 + 성향 태그(최대 4개), 클리어/미클리어 배지, 수정·삭제

**커뮤니티 게시판 (`/community`)**

- 리듬게임 탭 10개 + '전체' 탭 (탭마다 글 수 표시, 0건 탭도 유지)
- 말머리 필터 (자유/질문/정보/공략/대회) · 정렬 (최신/인기/댓글 많은)
- 글 목록 — 말머리·제목·본문 미리보기·작성자·추천/댓글/조회
- **글 20개 / 댓글 10개 페이지네이션** — 번호 이동, 탭·필터를 바꾸면 1페이지로
- 글 작성/수정 — 본인만 (남의 글은 403). 삭제는 **본인 또는 관리자**,
  삭제 시 댓글·추천·이미지 CASCADE
- 댓글 작성 · 삭제(**본인 또는 관리자**), 추천 토글 — 둘 다 캐시 카운트 즉시 재계산
- **관리자로 로그인하면 남의 글·댓글에도 삭제 버튼**이 붙습니다 (수정 버튼은 안 붙음).
  버튼에 "관리자 권한으로 남의 글을 삭제합니다" 툴팁을 달아 본인 글 삭제와 구분합니다
- 댓글 목록과 작성 폼은 구분선으로 분리 (마지막 댓글이 입력창처럼 읽히지 않게)
- **이미지를 본문 안 원하는 위치에 5장까지** — 커서 위치 삽입, 붙여넣기·드래그 업로드,
  **끌어서 위치 이동**(원래 자리에서 사라짐), 클릭 후 Backspace 로 삭제.
  붙여넣기는 서식 없이 글자만
- **드래그 중 드롭될 자리를 캐럿으로 표시** — 옮길 때와 새로 올릴 때 모두. 제자리
  드롭이면 표시하지 않음
- 글 상세는 `?view=1` 로 열 때만 조회수 +1

**아직 없는 것 (의도적)**

- ~~**일반 사용자의** 로그인/인증~~ — **붙었습니다.** 아이디/비밀번호 가입·로그인과
  Google·카카오·네이버 OAuth 가 모두 있고, `usePlayerId()` 는 세션 하나만 봅니다
  ([`lib/use-player.ts`](lib/use-player.ts)). 그 위에 걸려 있던 "API 가 클라이언트가 보낸
  `playerId` 를 믿는다" 는 문제도 함께 닫혔습니다 — 이름이 붙는 쓰기는 전부
  `requirePlayer(request)` 를 지나고, 요청에 섞인 `playerId` 는 스키마가 아예 받지
  않습니다 ([`lib/auth.ts`](lib/auth.ts) · [`lib/validation.ts`](lib/validation.ts) 머리말).
  아직 없는 것은 그 **다음** 단계입니다 — 신고·차단, MFA, 이메일 본인확인
- **로그인 2단계(MFA)** — 지금 로그인은 아이디+비밀번호 한 단계입니다. 시도 제한(IP당
  8회 실패 → 10분)은 DB 에 있어 재시작·다중 프로세스에도 유지되지만, 두 번째 확인
  수단(문자·인증 앱)은 없습니다
- 서식 (굵게·링크·인용 등) — 이미지 위치만 자유롭고, 글자는 평문입니다. 서식을 넣으려면
  마커 문법을 늘리거나 HTML 저장으로 가야 하는데, 후자는 sanitizer 를 들이는 결정입니다
- **이미지 리사이즈/썸네일** — 원본을 그대로 저장하고 그대로 내보냅니다. 폰 사진 한 장이
  3~5MB 라 **상세 화면에서** 그만큼 내려옵니다. 목록은 썸네일을 `next/image` 로 줄여
  받아 가볍지만(행당 수 KB — [`components/PostList.tsx`](components/PostList.tsx) 의
  `PostThumb`), 그건 목록 한 곳을 막은 것이지 저장 방식을 고친 게 아닙니다. 상세 화면과
  움직이는 GIF 는 그대로입니다. 실제로 먼저 붙여야 할 항목입니다
  (`lib/uploads.ts` 의 `save` 에서 리사이즈)
- **글에 붙지 않은 업로드 정리 배치** — 작성하다 그만두면 `post_images` 에 고아 행과
  파일이 남습니다 (`post_images_orphan_idx` 로 찾을 수 있게만 해뒀습니다)
- 게시판 검색, 대댓글, 신고·차단, 알림
- 제보 신고 / 이상 패턴 탐지 — 지금 방어선은 "익명은 임계값에 안 셈" 하나뿐입니다.
  대기 인원을 최대값으로 바꾸면서 한 건짜리 장난 제보가 값에 그대로 반영됩니다
  (중앙값이던 시절에는 묻혔습니다). 상한을 두거나 제보자당 1건만 세는 식으로
  막으려면 결국 계정이 필요합니다
- 점수 인증 — 요구사항에서 빠져 **제거했습니다** (아래 참고)
- 카카오맵 — 지도는 네이버로 붙였습니다. 카카오로 바꾸려면
  [`lib/naver-loader.ts`](lib/naver-loader.ts) 와 [`components/NaverMap.tsx`](components/NaverMap.tsx)
  두 파일만 교체하면 됩니다 (`MapPane` 이 구현을 고르는 지점)

> "클리어했습니다" 를 체크합니다. 자동 확정이 다시 필요해지면 그때 붙이는 쪽이
> 맞습니다 — 인증 없이는 어차피 어뷰징을 막을 수 없었습니다.
>
> ⚠ 기능이 추가되기 전에 만들어진 `.pglite` 에는 `score_submissions` / `scores` /
> `ocr_jobs` 테이블이 남아 있을 수 있습니다 (스키마 그룹은 "없으면 만든다"라서 제거를
> 따라잡지 못합니다). `npm run db:reset` 하거나 직접 `DROP TABLE` 하면 됩니다.

> - `db/seed-tier.sql` 의 곡 제목은 실제 Pump It Up 수록곡이지만, **등급 배치는 그 파일에서
>   생성한 가상 투표의 결과**입니다. 어떤 실제 서열표를 옮겨온 것이 아닙니다.
> - `db/seed-community.sql` 의 제보·리뷰·채보 평가 문장은 **전부 지어낸 것**입니다.
>   사운드 볼텍스 곡 제목은 실제 수록곡 이름이지만 **모드·레벨·등급 배치는 가상**이고,
>   아티스트는 확인하지 못해 비워 뒀습니다.
> - 대기 제보는 `now() - interval` 로 들어갑니다. 시드를 넣은 지 4시간
>   (`queue_ttl_minutes`) 이 지난 DB 에서는 "지금 대기" 표시가 비어 있는 게 **정상**입니다.
>   다시 보려면 `npm run db:reset` 하거나 UI 에서 직접 제보하세요.
>
> 운영 시 오락실은 네이버 지역 검색으로 초기 시딩 후 제보로 보정하세요 — `npm run arcades:import`.

### 실제 오락실 데이터 가져오기

네이버 **지역 검색 API** 로 실제 오락실을 가져와 `arcades` 를 채웁니다.

```bash
npm run arcades:import                          # 미리보기 (DB 를 건드리지 않습니다)
npm run arcades:import -- --write               # 반영 (이어서 하기 포함)
npm run arcades:import -- --write --drop-seed   # (가상) 8곳을 지우고 반영
npm run arcades:import -- --status              # 어디까지 했는지만 보기
npm run arcades:import -- --reset               # 진행 상태를 버리고 처음부터
npm run arcades:import -- --write --limit 500   # 오늘 호출 상한 조정
npm run arcades:import -- --query "홍대 오락실"  # 전국 목록 대신 직접 지정
```

**하루 한도와 이어서 하기**

질의는 전국 시·군·구 229곳 × 표현 4개 = **916건**입니다 (`lib/kr-regions.ts`).
네이버 지역 검색은 하루 25,000회 무료 한도가 있어, 기본 상한을 **20,000회**로 두고
넘으면 그 자리에서 멈춥니다. 다음 날 같은 명령을 다시 실행하면 이어서 합니다.

진행 상태는 `.arcade-import-state.json`(gitignore) 에 남고, **호출 1건마다** 저장합니다 —
중간에 죽어도 그날 쓴 호출 수를 잊지 않습니다. 날짜가 바뀌면 호출 카운터만 0 으로
돌아가고, 끝낸 질의 목록과 모은 장소는 유지됩니다.

`--drop-seed` 의 `(가상)` 데이터 삭제는 **질의 목록을 다 돈 실행에서만** 수행합니다.
절반만 모은 상태에서 지우면 다음 날까지 목록이 텅 빈 채로 남기 때문입니다.

**가져오는 것 / 못 가져오는 것**

| 항목 | 출처 |
|---|---|
| 이름 · 주소 · 좌표 | ✅ 지역 검색 응답 |
| **영업시간** | ❌ **응답에 필드가 없습니다** → `NULL`(정보 없음)로 들어갑니다 |
| 전화번호 | ❌ `telephone` 은 항상 빈 문자열입니다 (하위 호환용 잔재) |
| 장소 고유 ID | ❌ `link` 는 대부분 비어 있음 → 이름+주소로 식별합니다 |
| 보유 기종 | ❌ 네이버가 알 수 없는 정보 → 비어 있고, 기존처럼 제보로 채워집니다 |

영업시간을 가진 곳은 `map.naver.com` 이 내부적으로 쓰는 비공개 엔드포인트뿐이고,
이용약관이 금지하며 예고 없이 바뀌므로 쓰지 않았습니다. 대신 확인용 네이버 링크를
`arcades.source_ref` 에 남기니 관리자 화면에서 채우세요.

**준비**

`.env.example` 의 `NAVER_HUB_API_KEY_ID` / `NAVER_HUB_API_KEY` 를 채웁니다.
NCP 콘솔 > Services > **NAVER API HUB** 에서 지역 검색 이용 신청 후 발급합니다.

> ⚠ 2026-07-31 로 `developers.naver.com` 의 검색 API 지원이 끝났습니다. 지역 검색은
> **NAVER API HUB**(NCP 콘솔)로 이관됐고 자격증명·엔드포인트가 바뀌었습니다.
> 쇼핑·책·전문자료 검색은 이관 없이 완전 종료됐지만 지역 검색은 살아 있습니다.
>
> | | 구 (종료) | 신 |
> |---|---|---|
> | 엔드포인트 | `openapi.naver.com/v1/search/local.json` | `naverapihub.apigw.ntruss.com/search/v1/local` |
> | 인증 헤더 | `X-Naver-Client-Id` / `-Secret` | `X-NCP-APIGW-API-KEY-ID` / `-KEY` |
>
> 이관 전 변수명(`NAVER_SEARCH_CLIENT_ID/SECRET`)도 그대로 인식합니다.

섞이기 쉬운 키가 셋 있습니다 — 서로 **다른 값**이고, 2·3번으로는 검색이 안 됩니다(401):

1. `NAVER_HUB_API_KEY_ID` / `NAVER_HUB_API_KEY` — 검색 (NCP > NAVER API HUB)
2. `NEXT_PUBLIC_NAVER_MAP_KEY_ID` — 지도를 **그리는** NCP Maps 키
3. `NAVER_CLIENT_ID` / `NAVER_CLIENT_SECRET` — 네이버 **로그인**(OAuth)

**주의**

- 기본 DB(PGlite)는 한 프로세스만 열 수 있어, `next dev` 가 떠 있으면 `--write` 가
  거부됩니다. 먼저 dev 서버를 멈추세요 (실제 Postgres 를 쓰면 해당 없음).
- 지역 검색은 한 질의에 **최대 5건**이고 반경 지정이 없습니다. `start`(페이지네이션)는
  **무시되고**, `display` 는 안 보내면 기본값이 1 입니다(둘 다 실제 응답으로 확인).
  그래서 "지역 × 표현" 질의를 나열해 긁어모으는 방식입니다 (`lib/kr-regions.ts`).
- 네이버가 **안정된 장소 ID 를 주지 않습니다** — 응답의 `link` 는 대부분 비어 있고,
  값이 있어도 업체가 등록한 외부 홈페이지(인스타그램 등)입니다. 그래서 같은 업소를
  알아보는 기준은 **이름 + 주소**이고, `source_ref` 에는 그 둘로 만든 네이버 지도
  검색 링크를 넣습니다(영업시간을 확인할 때 열어 볼 주소를 겸합니다).
- `--drop-seed` 는 예시 오락실에 딸린 **가상 제보·리뷰까지 함께 지웁니다**. 지어낸
  리뷰가 실제 업소 행에 붙는 것을 막기 위한 것으로, 의도된 동작입니다.
- 다시 실행해도 `source_ref` 로 같은 업소를 찾아 갱신합니다(중복 없음). 이때 사람이
  채운 영업시간·기종은 **덮어쓰지 않습니다**.
