# 보안 — 무엇을 왜 고쳤나

> 작성 2026-09-11 · 대상: 로그인 시도 제한(①), API 권한 근거(②)
> 성능 기록은 [PERFORMANCE.md](../PERFORMANCE.md), 전체 상태는 [SSOT.md](../../SSOT.md) §8.

이 문서는 **결정의 근거**를 남깁니다. 무엇을 했는지는 diff 를 보면 되고, 왜 그 모양인지와
**무엇을 일부러 안 했는지**는 코드에 안 남습니다.

두 항목을 먼저 고른 이유는 같습니다 — 둘 다 **"방어가 있는 줄 알았는데 없던" 자리**입니다.
없는 방어를 추가하는 것보다, 있다고 착각하던 것을 고치는 쪽이 먼저입니다.

---

## ① 로그인 시도 제한이 무력했습니다

### 무엇이 문제였나

`lib/auth.ts` 의 잠금 키가 이랬습니다.

```ts
export function clientKey(request: Request): string {
  const forwarded = request.headers.get('x-forwarded-for');
  return forwarded?.split(',')[0]?.trim() || request.headers.get('x-real-ip') || 'local';
}
```

`X-Forwarded-For` 는 **클라이언트가 마음대로 보내는 헤더**입니다. 그 첫 값을 키로 쓰면
잠금 바구니를 공격자가 고르는 셈입니다.

```
X-Forwarded-For: 10.0.0.1  →  8회 실패, 잠김
X-Forwarded-For: 10.0.0.2  →  다시 8회
X-Forwarded-For: 10.0.0.3  →  다시 8회 …
```

**8회/10분 제한이 사실상 없었습니다.** 표적은 비밀번호 하나로 들어가는 관리자 계정입니다.
scrypt 라 대입이 느리긴 하지만, 제한이 없으면 느린 것은 시간 문제일 뿐입니다.

### 왜 "올바른 IP 를 찾기" 로 풀지 않았나

가장 먼저 떠오르는 해법은 "진짜 클라이언트 IP 를 제대로 뽑기" 입니다. 그런데
**라우트 핸들러는 소켓 주소를 볼 수 없습니다** — 표준 `Request` 에 그 정보가 없고,
Next 가 따로 주지도 않습니다. 프록시가 없으면 클라이언트를 식별할 방법이 **아예 없습니다.**

그래서 방향을 바꿨습니다. **막으려는 것이 무엇인가**를 다시 봤습니다 — 한 계정의
비밀번호 대입입니다. 그러면 세는 단위는 IP 가 아니라 **계정**이어야 합니다.
IP 는 위조되고 바뀌지만 **표적 계정은 바뀌지 않습니다.**

### 무엇을 했나

**로그인은 계정 단위로 셉니다** (`accountKey`).

```ts
export function accountKey(nickname: string): string {
  return `account:${nickname.normalize('NFC').trim().toLowerCase()}`;
}
```

대소문자를 접는 것이 중요합니다. DB 의 닉네임 중복 차단이 `lower()` 기준이라
(`migrate-027`) `Admin` 과 `admin` 은 **같은 계정**입니다. 키를 접지 않으면
대소문자만 바꿔가며 카운터를 초기화할 수 있어서, 고치려던 우회가 그대로 남습니다.
같은 이유로 공백과 한글 정규화(NFC/NFD)도 함께 접었습니다.

**IP 는 신뢰할 수 있을 때만 함께 셉니다.** `TRUSTED_PROXY_HOPS` 로 내가 운영하는
프록시가 몇 대인지 알려 주면, 체인의 **오른쪽에서** 그 수만큼 세어 프록시가 덧붙인
값만 믿습니다.

```
보낸 값:    X-Forwarded-For: 1.2.3.4           ← 위조
프록시 뒤:   1.2.3.4, 203.0.113.9               ← 프록시가 실제 주소를 뒤에 붙임
N=1 →      오른쪽 1번째 = 203.0.113.9  ✓       위조값을 지나침
```

프록시가 없으면(기본값 0) `null` 을 돌려 **아예 세지 않습니다.**
틀린 키로 세는 것은 안 세는 것보다 나쁩니다 — 방어가 있다고 착각하게 만듭니다.

**세는 곳은 DB 입니다** (`login_failures`, `migrate-052`). 처음에는 프로세스
메모리였는데, 목표 구성이 2 프로세스라 8회 제한이 4+4 로 새고 있었습니다. ②를
합치면서 저쪽의 DB 판으로 바꿨습니다 — 자세한 것은 ②의 표에.

### 계정 단위로 세면 생기는 문제 (알고 받아들였습니다)

**남의 계정을 일부러 잠글 수 있습니다.** 8번 틀리면 그 계정이 10분 잠기니, 계속 시도하면
특정 사용자를 로그인 못 하게 만들 수 있습니다.

그래도 이쪽을 골랐습니다. 비교하면 이렇습니다.

| | 무한 비밀번호 대입 | 10분 계정 잠금 |
|---|---|---|
| 결과 | **계정 탈취** | 로그인 지연 |
| 되돌릴 수 있나 | 아니오 | 10분 뒤 자동 |

같이 못 막을 때는 **되돌릴 수 없는 쪽**을 막습니다. 잠금 DoS 가 실제로 문제가 되면
고정 잠금 대신 지수 지연으로 바꾸는 것이 다음 수순이고, 키 설계는 그대로 씁니다.

### 가입은 여전히 제한이 없습니다 (숨기지 않습니다)

가입은 아직 계정이 없으니 계정 단위로 셀 수가 없습니다. IP 밖에 근거가 없고,
프록시가 없으면 그 IP 를 못 믿습니다. **그래서 프록시 없이 돌리면 가입 제한이 없습니다.**

예전 구현도 위조 가능한 키로 세고 있었으니 실효는 마찬가지였고, 지금은 그 사실이
드러나 있을 뿐입니다. 여기서 한 가지는 조심해야 했습니다 — `clientKey` 가 `null` 일 때
`` `signup:${null}` `` 로 키를 만들면 **전원이 한 바구니를 공유해 8회 실패에 가입이 전역으로
잠깁니다.** 고치려던 것보다 나빠지므로, 키가 없으면 세지 않도록 분기했습니다.

대량 가입을 막아야 하면 앞에 프록시를 두고 `TRUSTED_PROXY_HOPS` 를 주세요.
`npm run start:cluster` 는 홉을 하나 더하므로 자식에게 `1` 을 자동으로 넣습니다.

### 검증

`tests/rate-limit-key.test.ts` 12건 — 위조 헤더, 체인 길이 조작, 홉 수 오설정,
대소문자·NFC 우회를 고정했습니다. 로직이 아니라 **키**를 봅니다: 로직이 맞아도
키를 공격자가 고를 수 있으면 제한이 없는 것과 같기 때문입니다.

돌아가는 서버로도 실제 공격을 재현했습니다.

| 시나리오 | 결과 |
|---|---|
| `X-Forwarded-For` 를 12회 바꿔가며 틀린 비밀번호 | 8회까지 401 → **9회째부터 429** |
| 다른 계정(`othername1/2`) 로그인 시도 | 401 유지 — 전역 잠금 아님 |
| `LOCKADMIN` · `LockAdmin` · `  lockadmin  ` | 전부 429 — 대소문자 우회 차단 |

## ② API 권한의 근거를 세션으로 (R1)

### 무엇이 문제였나

대부분의 쓰기 API 가 **누가 보냈는지를 요청 본문에서 받아 그대로 믿었습니다.**

```ts
// POST /api/posts/:id/like
const playerId = parseId((body as { playerId?: unknown })?.playerId);
```

번호만 바꿔 보내면 **남의 이름으로** 추천·투표·제보·댓글을 할 수 있었습니다.
추천 수는 인기글 정렬의 근거이고, 투표는 서열표의 근거입니다 — 값이 아니라
**근거가 오염되는** 문제입니다.

읽기 쪽에도 같은 구멍이 있었습니다. `GET /api/charts/:id?playerId=` 가 "내 클리어·투표"를
표시하는 값이었는데, 번호를 바꾸면 **남이 무엇을 깼고 몇 점을 줬는지 훑을 수** 있었습니다.

### 왜 ①보다 뒤인가

②가 영향은 더 넓습니다. 그런데 ①은 **관리자 계정 탈취**로 이어지고, 관리자를 잡으면
②는 어차피 따라옵니다. 그리고 ①은 짧고 ②는 20여 파일입니다. 되돌릴 수 없는 쪽,
짧은 쪽이 먼저입니다.

### 어디에 있었나 — 다른 워크트리에서 가져왔습니다

②는 **`mfa-jwt-token-status-45e91a` 워크트리에 먼저 만들어져 있었습니다** (미커밋).
API 20곳 + 클라이언트 9곳 + `lib/auth.ts` + 테스트 + 문서가 함께 바뀌었고,
그 워크트리에는 클라이언트가 보낸 `playerId` 를 믿는 라우트가 **0곳**입니다.

**같은 것을 여기서 다시 만들지 않았습니다.** 중복이고, 합칠 때 20여 파일이 충돌하며,
같은 가드가 두 벌 생깁니다. 대신 그 작업을 읽어서 검토했습니다.

### 검토 결과 — 세 가지가 제대로 돼 있습니다

**익명 제보가 살아 있습니다.** 제보는 원래 로그인 없이도 됩니다(지나가다 본 것을
알려주는 자리라 가입을 요구하면 제보가 끊깁니다). 여기만 `requirePlayer` 가 아니라
`sessionPlayerId`(널 허용)를 써서 그 성질을 지켰고, 익명은 보유 기종 임계값에 세지
않는 기존 규칙도 그대로입니다. **전부 `requirePlayer` 로 덮으면 조용히 사라질 기능**이라
이게 가장 틀리기 쉬운 자리였습니다.

**읽기 경로의 정보 노출도 같이 막혔습니다.** `?playerId=` 를 세션 기준으로 바꿔,
로그인하지 않으면 개인 표시 없이 공개 정보만 나갑니다.

**클라이언트가 같이 바뀌었습니다.** 컴포넌트 9곳이 함께 수정돼 서버만 고치고 화면이
깨지는 상태가 아닙니다. 남아 있는 `playerId=` 검색 결과는 URL 파라미터가 아니라
React prop 입니다.

### 병합했습니다 (2026-09-11)

두 워크트리가 **같은 파일 12개**를 건드렸고, 그중 `lib/auth.ts` · `auth/login` ·
`auth/signup` 은 **①이 고친 바로 그 파일들**이었습니다. 그래서 순서를 정했습니다 —
**① 먼저 커밋 → ② 를 그 위에**. ①이 훨씬 작고 `clientKey` 의 시그니처가 바뀌었으므로
(문자열 → `string | null`), ②가 그걸 보고 맞추는 편이 쉽습니다.

겹치지 않는 16파일은 패치로 그대로 얹혔고, 겹친 6파일(`posts` · `posts/[id]` ·
`posts/[id]/like` · `arcades/[id]/reports` · `tier` · `validation.ts`)은 손으로
합쳤습니다. `like` 는 그 사이 이쪽에서 **토글 → `PUT`/`DELETE`** 로 바뀌어 있어서
저쪽의 `POST` 판을 그대로 쓸 수 없었습니다.

**잠금은 두 벌 중 좋은 쪽을 하나씩 남겼습니다.**

| | 이쪽(①) | 저쪽(②) | 남긴 것 |
|---|---|---|---|
| 세는 단위 | 계정 키(대소문자·NFC 정규화) | IP | **둘 다** — 계정 키로 세고, 위조 못 하는 IP 만 |
| 저장 위치 | 프로세스 메모리 | DB(`login_failures`) | **DB** — 프로세스 2개면 메모리는 각자 셉니다 |

메모리 판은 목표 구성(2 프로세스)에서 **잠금이 절반씩 새는** 문제가 있었습니다.
8회 제한이 사실상 16회가 됩니다. `db/migrate-052-login-failures.sql` 로 옮겼습니다.

### 정말 막혔는지 — 실제 서버로 확인했습니다

테스트(24개)와 별개로, 운영 빌드에 요청을 넣어 봤습니다.

| 해 본 것 | 결과 |
|---|---|
| A 로 로그인해 글을 쓰며 본문에 **B 의 번호**를 적음 | 글쓴이 **A** |
| 비로그인 글쓰기 | `401` — 아무것도 저장되지 않음 |
| B 가 A 의 글을 수정(본문에 A 번호) | `403` |
| 비로그인이 `?playerId=A` 로 A 의 글 삭제 | `401` |
| B 가 `?playerId=A` + 본문 A 번호로 추천 | `post_likes` 에 남은 사람은 **B** |
| 비로그인 제보(본문에 A 번호) | `201` · `player_id = NULL` (익명) |
| 비로그인이 `?playerId=B` 로 서열표 조회 | `myClear = false` (B 본인은 `true`) |

마지막 줄이 읽기 쪽 노출이 막혔다는 증거입니다 — 같은 URL 인데 **쿠키가 있을 때만**
개인 표시가 나옵니다.

### 딸려 온 것 — 부하 하네스의 미해결 401

`load-test/k6-write.js` 는 세션 쓰기(즐겨찾기)를 **"동시 VU 면 일부가 401"** 이라는
이유로 빼 두고 있었습니다. R1 이후에는 모든 쓰기가 세션을 요구하므로 피할 수 없어
다시 봤고, 원인이 나왔습니다 — **k6 의 쿠키 항아리는 반복(iteration)마다 초기화됩니다.**
가입은 첫 반복에서 한 번뿐인데 "세션을 세웠다" 는 플래그는 남아 있어서, 2회차부터
쿠키 없이 던지고 있었습니다. 동시성 문제가 아니었습니다.

쿠키 문자열을 직접 들고 다니게 고쳤더니 실패율 43% → **0%** 가 됐고, 즐겨찾기도
믹스에 돌아왔습니다. 쏠림 시나리오에서 `arcade_machines` 가 실제로 뒤집히는 것까지
확인했습니다(서로 다른 계정 21개가 임계값을 채웁니다).

### 마이그레이션 번호도 정리했습니다

두 브랜치가 049 에서 갈라져 같은 번호를 서로 다른 것에 쓰고 있었습니다. 이쪽이
뒤로 물러났습니다 — 저쪽이 셋(050 player-email · 051 email-verification ·
052 login-failures)이고 이쪽이 둘이라, 적게 움직이는 쪽입니다.

| | 전 | 후 |
|---|---|---|
| 대기 제보 정리 인덱스 | `migrate-050-queue-purge-index.sql` | **`migrate-053-…`** |
| 로그인 실패 표 | `migrate-051-login-failures.sql` | **`migrate-052-…`** (저쪽과 같은 이름) |

로그인 실패 표는 **일부러 저쪽 번호를 그대로 가져왔습니다.** 같은 DDL 이라 이름이
같으면 합칠 때 한 파일이 되고, 다르면 같은 표를 두 이름으로 적용하게 됩니다.
(본문은 같고 머리말만 다릅니다 — 저쪽은 "8프로세스 → 64회", 이 브랜치의 권고 구성은
2프로세스라 "16회" 로 고쳤습니다.)

DB 는 손대지 않았습니다. 러너가 번호가 아니라 **파일 이름**으로 이력을 남기고
(`schema_migrations.name`), 확인해 보니 개발 DB 에는 이미 저쪽 이름으로 052 가
적용돼 있었습니다. 새 이름이 다시 돌아도 전부 `IF NOT EXISTS` 라 아무 일도
일어나지 않습니다. 049 다음이 053 인 이유는 `migrate-053` 머리말에 적어 뒀습니다.

## 안 한 것과 그 이유

| | 왜 안 했나 |
|---|---|
| **JWT 도입** | 이미 같은 것을 쓰고 있습니다 — `sealPayload` 가 `base64url(payload).HMAC-SHA256` 이라 **HS256** 입니다. 표준 JWT 와의 차이는 헤더 조각 하나뿐이고, 지금 그걸로 얻는 것이 없습니다. 외부 서비스가 토큰을 검증해야 할 때 하면 됩니다 |
| **localStorage + Bearer 로 이전** | **보안 하향입니다.** 지금 세션 쿠키는 HttpOnly 라 스크립트가 못 읽습니다. localStorage 로 옮기면 읽힙니다. Next 한 몸 구조라 쿠키가 불편하지도 않습니다 |
| **토큰 회수 수단** | 다음 항목입니다. 7일 무상태 토큰이라 개별 무효화가 안 되고, 막으려면 `AUTH_SECRET` 교체 = 전원 로그아웃뿐입니다. `players.token_epoch` 한 컬럼으로 풀 수 있습니다(관리자 경로가 이미 요청마다 DB 를 보는 것과 같은 패턴) |
| **`ADMIN_PASSWORD` 미설정 시 로그인 503** (R11) | 절반은 의도된 안전장치입니다 — 운영에서 기본 비밀번호(`admin1234`)를 쓰지 않고 **닫는 쪽**입니다. 문제는 그 검사가 라우트 전체를 막아 일반 로그인까지 죽는 것이고, 검사를 관리자 분기 안으로 옮기면 끝납니다. ①②보다 급하지 않습니다 |

## 손대지 않아도 되는 것 (확인했습니다)

여기에 시간을 쓰지 말자는 뜻으로 남깁니다.

| | 상태 |
|---|---|
| XSS | **구조적으로 닫혀 있습니다.** 본문이 HTML 이 아니라 JSON 문서 트리이고, 화이트리스트 밖 노드는 버립니다. `dangerouslySetInnerHTML` 이 **0곳**이고 색·크기는 닫힌 목록입니다 |
| 업로드 | 매직바이트로 형식을 판별하고(확장자·Content-Type 을 믿지 않음), MIME 허용목록 + 타입별 크기 상한(사진 5MB · 영상 50MB) |
| SQL 인젝션 | 전부 파라미터 바인딩. 값을 문자열로 이어 붙이는 쿼리가 없습니다 |
| 관리자 권한 회수 | 쿠키의 `adm` 을 믿지 않고 **요청마다 DB 를 다시 봅니다** — 권한을 뗀 계정의 토큰이 만료 전에도 바로 막힙니다 |
| CSRF | `SameSite=lax` + JSON 본문이라 고전적 폼 CSRF 는 막힙니다. OAuth `state` 쿠키도 서명돼 있습니다 |
| 비밀번호 저장 | scrypt(salt 16B · key 64B), 형식에 알고리즘 이름을 넣어 나중에 파라미터를 올릴 여지를 남겼습니다 |
